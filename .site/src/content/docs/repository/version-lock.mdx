A lab result means something only for the exact versions that produced it. `versions.lock.yaml` holds every pinned version, commit, image digest and checksum the lab uses. Roles, values files and image builds read their versions from it and hard-code none. A component the lab has not decided yet is `null` with a reason, and any target that needs it refuses to run.

## Components

Each component has a `kind`, a `value`, a `reason` and a `source`, and validates against `schemas/versions-lock.schema.json`.

| Kind | Example | Meaning |
|---|---|---|
| `version` | `k8s.kubernetes` | A release version |
| `git-sha` | `ns3.simai` | A full commit SHA of an upstream repository |
| `image-digest` | `ibsim.image` | An OCI digest, so an image is pinned by content, not by tag |
| `checksum` | `k8s.containerd_archive` | The sha256 a role checks a download against |
| `observed` | `lab.guest_kernel` | A value read from a running environment, such as a guest kernel release |

The `reason` says why this value was chosen, and the `source` says where it was read. For example, the lab takes the latest Kubernetes v1.36 patch rather than v1.37, because the Cilium 1.20 compatibility table covers only 1.33 to 1.36 ([ADR 0001](/docs/adr/0001-kubernetes-stack/) section 3).

## Scopes

A scope lists the components one part of the lab needs: `lab` the RXE guests and the host, `k8s` the cluster, `k8s-rdma` the hostNetwork RDMA and Multus scenarios, `ibsim` Track B, `ns3` Track C, `fleet` the cel1 cluster and `tooling` the control node. `make versions SCOPE=<name>` fails when any of them is still `null`, and the targets of that part depend on it. `make versions` alone also fails when the Python tooling in `.venv` drifts from `tooling.*`. This list is read from the lock at build time.

## What pinning costs

The `common` role installs the exact locked package versions. When the Ubuntu archive moves rdma-core up, the old version drops out of its index and `make bootstrap` fails, naming the cause. The fix is to probe again and pin the lock ([troubleshooting](/docs/troubleshooting/) section 2). Track B, Track C and the RDMA test image avoid this by installing from a dated Ubuntu snapshot, `20261115T000000Z`, which never changes.

The image digests go further. A rebuild of the Track C image from nothing, with the cache emptied, had to give the pinned digest, and did. `guest.sh build` exports with `SOURCE_DATE_EPOCH` and `rewrite-timestamp`, and the build removes the apt lists, logs and caches that carry build-time state. The Track B image follows the same rules and rebuilt to its pinned ID from two wiped guests ([ADR 0002](/docs/adr/0002-execution-environments/) section 5).

## make collect, the guests against the lock

`make collect` runs the scenario `vm-environment`. It snapshots the host and the workers and compares every `lab.*` value of the lock that the guests report with what they report. No traffic runs.
