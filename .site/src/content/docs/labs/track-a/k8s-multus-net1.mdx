Workloads that need a second network keep Cilium for everything else. This scenario gives two ordinary pods, on different workers, a second interface `net1` on the lab network. Multus adds it beside Cilium's `eth0`, macvlan creates it on the lab NIC, and Whereabouts picks its address from a cluster-wide pool. The run then recreates the pods and reboots a worker, because the CNI layout is most fragile at boot.

## Goal

Show that `net1` works across nodes on the lab NIC without moving the default route or breaking `eth0`, that Whereabouts hands out unique addresses and gives them back, and that a pod created right after a worker reboot waits for Multus and starts with `net1`, never with `eth0` alone.

## Concepts it uses

- [Multus, Whereabouts and macvlan](/concepts/kubernetes-networking/).
- [CNI](/concepts/kubernetes-networking/) and why the order of files in `/etc/cni/net.d` decides which plugin runs.

## Before you start

| Item | Value |
|---|---|
| Profile | `lab`: `cp1` 2 vCPU, 4 GiB, and `worker1`, `worker2` 4 vCPU, 6 GiB each |
| Versions | Multus v4.3.2 thick plugin from a repo-local chart, Whereabouts v0.9.4, Cilium chart 1.20.4 |
| Inventory | `lab_rdma_nic` must be the same on every worker. The harness renames both lab NICs `lab0` at first boot |
| Version lock | `make versions SCOPE=k8s-rdma` must return 0 |

**Time taken.** <Duration id="a-multus-time" />. Most of it is the worker reboot, about 97 s, because the Whereabouts daemon container does not stop on SIGTERM and systemd kills it after 90 s. Multus wrote its file 18.5 to 19.0 s after the boot in the runs after the layout change.

## Run it

```bash
make addons ENV=lab KUBECONFIG_FILE=.lab/kubeconfig   # Cilium, Multus, Whereabouts in that order
make cni-migrate                                      # only on a cluster built before the CNI layout change
make k8s-multus-test                                  # this scenario
```

The runner renders the NetworkAttachmentDefinition from the inventory alone. `python -m run.multus render` prints it.

```yaml
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: rdma-lab-net
  namespace: rdma-lab
spec:
  config: '{"cniVersion": "0.3.1", "name": "rdma-lab-net", "type": "macvlan", "master":
    "lab0", "mode": "bridge", "ipam": {"type": "whereabouts", "range": "10.77.0.0/24",
    "range_start": "10.77.0.100", "range_end": "10.77.0.199"}}'
```

That render is what `python -m run.multus render` printed for the lab inventory on 2026-11-16. With a worker whose `lab_rdma_nic` differed, render refused with exit 2, because one attachment names one macvlan master for every node. The test pods are busybox at the PodSecurity `restricted` level.

## What every check proves

<ScenarioChecks spec="a-soft-roce/k8s-multus-net1" />

`pod-at-boot-waits-for-multus` is the subtle one. The worker reboots, and as soon as SSH answers a client pod that tolerates every NoSchedule taint is created there, so only the container runtime can hold it. The runner then samples containerd's NetworkReady and the CNI directory every half second while `00-multus.conf` is absent. Every sample must show no network, and the pod's first `RunPodSandbox` must come after the file's birth.

## The stock paths of both charts

The charts' defaults put both files in the directory containerd reads: Cilium's `cni.confPath` is `/etc/cni/net.d`, and Multus's `multusAutoconfigDir` is `/host/etc/cni/net.d`. On 2026-11-25 one cluster was built from wiped guests with those defaults. Run `20261125T131218Z` failed the same three checks as the break above: containerd reported a network from boot+6.2 s, and the pod's sandbox began before Multus wrote its file. After `make addons ENV=lab` and `make cni-migrate` moved the same cluster to the lab layout, run `20261125T132655Z` passed all 14.

<Excerpt id="slides-net1-break" />

The test pod tolerates every NoSchedule taint, so it is the earliest pod a node can run. `tests/integration/qemu-lab/probe-boot-window.sh` asks what happens to ordinary pods on the same cluster. It reboots worker2 with three pods already running there, which the kubelet starts again in new sandboxes (`keepers`), or with one pod created while the node is down, which is scheduled once the node is Ready again (`waiters`). Multus wrote its file 17.7 to 19.8 s after boot, and each of those sandboxes began after it, so 0 of 20 pod starts lost `net1` with either layout. With one more init container that starts the Multus daemon 30 s later, the file appeared 48.6 to 50.2 s after boot. With the stock paths the sandboxes still began 28.1 to 32.0 s after boot, before the file, and 12 of 12 pods came back Ready without `net1`. With the lab layout every sandbox waited for the file, and 0 of 12 lost it. The restarted pods kept the `network-status` annotation of their old sandbox, with `net1` and an eth0 address that was no longer the pod's, and the waiting pods had none. So the stock paths are safe only while Multus is quicker than the kubelet, and a stale annotation still lists the `net1` the pod lost.

<Excerpt id="slides-boot-window" />

After the probe the delay was removed, the cluster was returned to the lab layout, and run `20261125T150004Z` passed all 14 checks.

## Questions to think about

- The Multus daemon deletes `00-multus.conf` when it stops. With Cilium's file still in `/etc/cni/net.d`, what does containerd do for a pod created in the 18 seconds after a boot, and why is there no error?
- Why must the boot-time pod tolerate every NoSchedule taint for the check to mean anything? What would hold it otherwise?
- macvlan children carry their own MAC addresses. What must the virtual NIC and the cable do for them to work, and how did the extra-MAC probe show it?
- A pod that asked Multus for `default-route` through the lab network kept its default route on `eth0`. How does the break for `default-route-on-eth0` move it instead?

## What the result means and does not mean

The run shows that Multus adds `net1` beside Cilium without moving the default route or breaking `eth0` across nodes, that Whereabouts hands out cluster-wide addresses without duplicates and releases them, and that a pod created at boot waits for Multus.

> [!NOTE]
> `net1` carries IP only. RXE lists the `net1` addresses as GIDs, but no pod got an RDMA device on `net1`, and nothing here shows an RDMA endpoint for a `net1` address. Hubble and Cilium NetworkPolicy were not tested on `net1` or on hostNetwork pods. The spec's result kind is `software-cluster-test`.
