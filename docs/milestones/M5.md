## 5. Image and the rebuild from clean

`images/ns3/Dockerfile` has two stages from the pinned base. The build stage installs build-essential, cmake, python3, git and ca-certificates from the snapshot, fetches the sources by commit, runs SimAI's `./scripts/build.sh -c ns3` unchanged, then copies `rfl-star.cc` into the ns-3 scratch directory and builds it. The final stage installs python3 and time from the snapshot and copies only the ns-3 `build/` outputs, SimAI's `example/` and `inputs/`, and the source record. The image runs as `10001:10001`.

A build of the same inputs writes the same bytes for three reasons.

- `apt-snapshot-install` removes the apt lists, the dpkg and apt logs, the ldconfig aux cache and every `__pycache__`, all of which carry build-time state.

- `guest.sh build` exports with `type=image,rewrite-timestamp=true,unpack=false` and `SOURCE_DATE_EPOCH`. BuildKit 0.30.1 refuses `rewrite-timestamp` with the unpack that `type=docker` implies (`probe/03-rewrite-timestamp.txt`). Docker unpacks the image when a container starts.

## 8. How far above the bound, and why

The bound is `8 × payload_bytes / bottleneck_bit_per_sec` plus the one-way propagation delay: 8 × 1000000 / 10^11 s = 80000 ns, plus 2 × 1000 ns, gives 82000 ns. The model's FCT is 88092 ns, 6092 ns or 7.43% above it. `network.fct_bound` derives the FCT of one flow alone from the model's mechanics, and it gives exactly 88092 ns. 0 ns stays unexplained.

| Part | ns | Why |
|---|---:|---|
| Payload at 100 Gbps | 80000 | the first term of the bound |
| Headers and integer nanoseconds | 4000 | Each packet is 1052 B on the wire, 52 B more than its payload. 1052 B take 84.16 ns at 100 Gbps, which the model truncates to 84 ns. 1000 × 84 − 80000 = 4000. The truncation makes the model send 1052 B per 84 ns, 100.19 Gbps on the wire |
| Propagation, sender to receiver | 2000 | the second term of the bound |
| Store and forward of the last packet | 84 | The switch forwards a packet only once it has fully arrived, so the last packet crosses the second link after the first |
| The last ACK returns | 2008 | The QP completes when the ACK reaches the sender: two 4 ns transmissions of 60 B and 2000 ns of propagation |
| Total | 88092 | equal to the measured FCT |

The first run of `pfc-bottleneck`, with one QP, is the reason for the four QPs. Section 11 has the cause. `config-applied` itself failed on its first run, `20261116T135412Z`, before any deliberate break: the wire sizes did not match my reading of the headers (section 11).

## 11. Model behavior that M6 inherits

Each item was found in this milestone and is backed by a run or a line of code.

1. **The L2 header is 14 bytes.** This fork's `PppHeader` writes the protocol and 12 zero bytes (`ppp-header.cc:85-90`). The first c-02 run failed `config-applied` with 52 B per data packet and 60 B per ACK against the 40 B and 48 B I had derived. The constants now follow the code, and the expected FCT matches to the nanosecond.
2. **A PFC RESUME crashes a host with fewer QPs than the paused priority index.** `QbbNetDevice::Resume(qIndex)` reads `m_rdmaEQ->GetQp(qIndex)` (`qbb-net-device.cc:463`), which is `m_qps[qIndex]`, the host's QP list indexed by priority (`rdma-queue-pair.cc:253`). The first `pfc-bottleneck` run died with SIGSEGV, exit 139, before writing any counter (run `20261116T135921Z`). A probe with one, three and four QPs on priority 3 crashed, crashed and completed with 25 PAUSE and 25 RESUME (`evidence/m5/probe/05-pfc-resume-qp-index.txt`). An incast with PFC on and one QP per sender will hit this. M6 needs a minimal patch or at least priority + 1 QPs per host.
3. **"PFC off" means the hosts ignore PAUSE.** With `QbbEnabled` false, the switch still sends PAUSE (`switch-node.cc:94-95`) and the host returns before its trace (`qbb-net-device.cc:492`). A run with a 200 kB buffer behind the bottleneck sent 1 PFC frame, printed 89222 MMU drops and did not finish the flow in 10 ms (`evidence/m5/probe/06-mmu-drop-probe.txt`).
4. **`DynamicThreshold` and `QcnEnabled` change nothing.** Section 7.
5. **The receiver's ECN tallies wrap.** `RdmaRxQueuePair::ECNAccount` keeps `qfb` and `total` as `uint16_t` (`rdma-queue-pair.h:117`). `rfl-star` counts marks from trace sources instead.
6. **libpoint-to-point needs libmtp but does not link it.** It uses `MtpInterface`'s lock. Ubuntu's gcc links with `--as-needed`, so the first image build failed to link `rfl-star` with an undefined `g_e_inCriticalSection` (`evidence/m5/image-build-0-link-error.log`). `rfl-star` now reads `MtpInterface::isEnabled()`, which keeps libmtp in the link and records in `resolved.tsv` that one thread ran every event.
7. **DCQCN defaults differ from SimAI's configuration.** The model defaults (`RateAI` 5 Mb/s, `RateHAI` 50 Mb/s, `EwmaGain` 1/16, `RPTimer` 1500 us) are not SimAI.conf's values (50 Mb/s, 100 Mb/s, 1/256, 900 us). M5 sets none, because no CNP arrives. M6 must set and read back each one.

## 12. What the results mean and do not mean

- **They are model behavior.** The FCT, the counters and the absence of pauses and marks are what ns-3-alibabacloud `3e0c7c1` computes for these inputs. They do not show how a ConnectX NIC, a switch ASIC or a cable behaves, and they are not a performance figure of this host.
- **The baseline shows the features are off the path, not that they work.** PFC, ECN and DCQCN were on and nothing triggered them. The breaks show the counters can see pauses, marks and drops. Whether the profiles act as intended under congestion is M6's question.
- **The FCT is exact for this case only.** The decomposition of section 8 holds for one flow alone on a path of equal-rate links. It is not a general formula.
- **The SimAI example is a smoke test.** It shows the backend builds, runs and repeats. Its 0.389 s of simulated time for a microAllReduce on eight H20 GPUs is a model output, not a prediction of training time.
- **Simulator cost is not network performance.** 4.0 s and 2.5 GB for the example, 0.023 s and 61 MB for `rfl-star`, are costs of one process in one VM on a shared host.
- **The Track C link rates are model inputs.** They are not comparable with the RXE bandwidth of Track A.
