## 2. Behavior

**Device creation.** The `rxe` role first reads `rdma -j link show`. If a device with the same name sits on another NIC, or another RDMA device sits on the lab NIC, the role fails and changes nothing. Then it installs and starts the unit. The unit's script waits up to 90 seconds for the lab NIC to come up with its address. It then runs `rdma link add` only when `rxe0` does not exist. The script never deletes a device. The same unit runs at every boot.

**Runner.** `make rxe-test` starts with `rfl run-init`, records an `rfl run-check` for each declared check, and ends with `rfl run-finalize`. Every guest process runs under `timeout -k 5 <seconds>` with the environment variable `RFL_RUN=<run-id>`. The server counts as ready when `rdma -j resource show cm_id` shows a LISTEN cm_id of that tool on its port. The client starts only after the server is ready. Each process leaves its stdout, stderr and exit code in `raw/<check>/<guest>-<role>.*`. rping and perftest both resolve addresses through RDMA CM (`rping`, perftest `-R`) and set no GID index. The recorded GID index 1 is the value rdma_cm chose.

**Path check.** During the test, tcpdump captures all traffic on the lab NIC and on the management NIC of both workers. Packet capture is limited to the lab interfaces, so on the management NIC it takes only RoCEv2 (UDP 4791) and SSH connection starts (SYN). The SYN count proves that the capture was alive. A pure Python parser on the control node counts the pcap.

**Why these options.** The `ib_write_bw --help` output and the `rping` usage were checked in the guest first (`docs/milestones/evidence/m1/probe.log`). perftest runs with `-d rxe0 -R -p 18515 -s 4096 -n 1000 -F --report_gbits`, and rping runs with `-a <server address> -p 7174 -C 10 -S 64 -V -v`.

## 5. Bandwidth record

Bandwidth has no pass threshold. These are software measurements of this host and guest combination. They do not indicate HCA performance.

| Metric | Passed runs | Min | Median | Max |
|---|---:|---:|---:|---:|
| `rdma_read.bw_average` | 10 | 0.43 | 2.07 | 2.62 |
| `rdma_write.bw_average` | 10 | 0.49 | 2.14 | 2.75 |
| `rdma_send.bw_average` | 10 | 0.41 | 2.22 | 2.88 |

The unit is the perftest Gb/sec. Read the numbers together with the following (`.lab/limiter/20261115T023119Z/`).

- The setting `-n 1000 -s 4096` is a short burst that sends 4MB in about 16ms. Under the same conditions, sending continuously for 10 seconds with `ib_write_bw -D 10` averaged 0.88 and 0.89 Gb/sec.
- TCP over the same lab NIC sent 2000MiB in 8.77 seconds. That is about 1.9 Gb/sec. The virtual cable carries more than twice the sustained RXE rate.
- During the measurement, the host was busy with other work. Load average was 30 (24 cores), CPU idle 1.8%, guest steal 16%. The QEMU management threads were at 30–40% and not saturated. The vCPU threads were around 90% because of the perftest CQ busy-poll.
- So the limiting factor was not isolated. Host contention is the most likely cause, but no measurement confirmed it. If a performance comparison is needed, measure again with a sustained `-D` test on an idle host.

## 6. Findings

**The failure class of the link down fault.** When the lab NIC of worker1 goes down with `ip link set down`, the run ends as failed with no processes left, and it passes again once the link is up. But the failure class is not `timeout`.

- systemd-networkd removes the static address from a NIC that lost carrier (`IgnoreCarrierLoss=no` is the default).
- So the rping server ends at once with `rdma_bind_addr: Cannot assign requested address`, and the perftest server ends at once with `Port number 1 state is Down`. The class is `command-failed`, and the device and path checks are `assertion-failed`.
- Taking down the client-side (worker2) link also ends the run at once, with `RDMA_CM_EVENT_ADDR_ERROR, error -19` (development run `20261115T020504Z`).
- In the fault where the link stays up and only frames are dropped (`netem loss 100%`), the `rping` client waited for a connection reply, hit the 30-second runner limit, and ended with exit code 124 and class `timeout`. The perftest client of this run printed only `Received 10 times ADDR_ERROR` and gave no errno, so it stayed `command-failed`.

The "timeout class" of criterion 7 does not occur with a link down fault. The tools fail at once, so recording a timeout would be false. The classification was left unchanged.

**A path that leaks onto the management network during link down.** While the address is down, the kernel sends the peer RDMA address over the default route, which is the management NIC (`route-via-lab-nic`: `worker1 routes 10.77.0.13 via enp0s3`). RDMA CM does not connect, because the management NIC has no RDMA device. Plain IP traffic can leave over the management network. To block it, keep the address with netplan `ignore-carrier: true`, or add an unreachable route for the lab network. Neither was applied this time.

**The cost of pinning versions.** The `common` role installs the exact locked versions. When noble-updates moves rdma-core up, the old version drops out of the index and `make bootstrap` fails. The failure message names the cause. The fix is to probe again and pin the lock.

## 7. Cleanup and reset

When the runner was killed with SIGKILL, worker1 kept two tcpdumps and the waiting `ib_read_bw` server, with their `timeout` and `sh` wrappers, as 9 processes. Captures were also left on worker2 (`30-leftovers-before-cleanup.log`). A decoy `sleep 900` with another run id was there too.

`make cleanup RUN=20261115T022855Z` stopped only the processes of that run and deleted only `/var/tmp/rfl/20261115T022855Z` (`31`). Afterwards the decoy process, its directory and `rxe0` on both workers were still there, and the guests kept running (`32`, `33`). The decoy was removed separately with `make cleanup RUN=20991231T235959Z` (`34`).
