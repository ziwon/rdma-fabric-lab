## 2. 동작

**장치 생성.** `rxe` 역할은 먼저 `rdma -j link show`를 읽는다. 같은 이름의 장치가 다른 NIC에 있거나 lab NIC에 다른 RDMA 장치가 있으면 아무것도 바꾸지 않고 실패한다. 그다음 unit을 설치하고 시작한다. unit의 스크립트는 lab NIC가 올라오고 주소를 가질 때까지 최대 90초 기다린 뒤, `rxe0`가 없을 때만 `rdma link add`를 실행한다. 스크립트는 장치를 지우지 않는다. 같은 unit이 부팅 때마다 돈다.

**러너.** `make rxe-test`는 `rfl run-init`으로 시작해 선언된 검사마다 `rfl run-check`를 남기고 `rfl run-finalize`로 끝난다. 게스트 프로세스는 모두 `timeout -k 5 <초>` 아래에서 `RFL_RUN=<run-id>` 환경 변수를 갖고 돈다. 서버 준비는 `rdma -j resource show cm_id`에 해당 도구의 LISTEN cm_id가 그 포트로 나타나는 것으로 판정한다. 클라이언트는 서버 준비 후에만 시작한다. 프로세스마다 stdout, stderr, 종료 코드를 `raw/<check>/<guest>-<role>.*`에 남긴다. rping과 perftest는 모두 RDMA CM(`rping`, perftest `-R`)으로 주소를 해석하고 GID index를 지정하지 않는다. 기록된 GID index 1은 rdma_cm이 고른 값이다.

**경로 검사.** 시험 동안 두 worker의 lab NIC 전체와 관리 NIC를 tcpdump로 잡는다. 관리 NIC는 PLAN 11.2에 따라 RoCEv2(UDP 4791)와 SSH 연결 시작(SYN)만 잡는다. SYN 수는 그 캡처가 살아 있었다는 증거다. pcap은 제어 노드의 순수 Python 파서로 센다.

**옵션 선택 근거.** 게스트에서 `ib_write_bw --help`와 `rping` 사용법을 먼저 확인했다(`docs/milestones/evidence/m1/probe.log`). perftest는 `-d rxe0 -R -p 18515 -s 4096 -n 1000 -F --report_gbits`, rping은 `-a <서버 주소> -p 7174 -C 10 -S 64 -V -v`로 돈다.

## 5. 대역폭 기록

대역폭에는 합격선이 없다. 이 호스트와 이 게스트 조합의 소프트웨어 측정값이다. HCA 성능을 뜻하지 않는다.

| 지표 | passed run 수 | 최소 | 중앙값 | 최대 |
|---|---:|---:|---:|---:|
| `rdma_read.bw_average` | 10 | 0.43 | 2.07 | 2.62 |
| `rdma_write.bw_average` | 10 | 0.49 | 2.14 | 2.75 |
| `rdma_send.bw_average` | 10 | 0.41 | 2.22 | 2.88 |

단위는 perftest의 Gb/sec다. 해석할 때 다음을 함께 본다(`.lab/limiter/20261115T023119Z/`).

- 설정값 `-n 1000 -s 4096`은 4MB를 약 16ms 동안 보내는 짧은 burst다. 같은 조건에서 `ib_write_bw -D 10`으로 10초를 이어 보내면 평균 0.88, 0.89 Gb/sec였다.
- 같은 lab NIC 위 TCP는 2000MiB를 8.77초에 보냈다. 약 1.9 Gb/sec다. 가상 케이블이 RXE 지속 속도의 두 배 이상을 나른다.
- 측정하는 동안 호스트는 다른 작업으로 바빴다. load average 30(24코어), CPU idle 1.8%, 게스트 steal 16%였다. QEMU 관리 스레드는 30–40%로 포화되지 않았다. vCPU 스레드는 perftest의 CQ busy-poll 때문에 90% 안팎이었다.
- 따라서 한계 요인은 분리하지 못했다. 호스트 경합이 가장 유력하지만 측정으로 확정하지 않았다. 성능 비교가 필요하면 호스트를 비운 상태에서 `-D` 지속 시험으로 다시 잰다.

## 6. 발견 사항

**링크 down 장애의 실패 분류.** worker1의 lab NIC를 `ip link set down`으로 내리면 run은 failed로 끝나고 남은 프로세스는 없으며, 링크를 올리면 다시 통과한다. 그러나 실패 분류는 `timeout`이 아니다.

- systemd-networkd는 carrier를 잃은 NIC에서 고정 주소를 내린다(`IgnoreCarrierLoss=no`가 기본값).
- 그래서 rping 서버는 `rdma_bind_addr: Cannot assign requested address`로, perftest 서버는 `Port number 1 state is Down`으로 바로 끝난다. 분류는 `command-failed`이고 장치·경로 검사는 `assertion-failed`다.
- 클라이언트 쪽(worker2) 링크를 내려도 `RDMA_CM_EVENT_ADDR_ERROR, error -19`로 바로 끝난다(개발 run `20261115T020504Z`).
- 링크는 살아 있고 프레임만 버려지는 장애(`netem loss 100%`)에서는 `rping` 클라이언트가 연결 응답을 기다리다 러너의 30초 제한에 걸려 종료 코드 124, 분류 `timeout`으로 끝났다. 이 run의 perftest 클라이언트는 `Received 10 times ADDR_ERROR`만 출력하고 errno를 주지 않아 `command-failed`로 남았다.

기준 7의 "timeout 분류"는 링크 down 장애로는 나오지 않는다. 도구가 바로 실패하는데 timeout으로 기록하면 거짓이 되므로 분류를 바꾸지 않았다.

**링크 down 때 관리망으로 새는 경로.** 주소가 내려간 동안 커널은 상대 RDMA 주소를 기본 경로, 즉 관리 NIC로 보낸다(`route-via-lab-nic`: `worker1 routes 10.77.0.13 via enp0s3`). RDMA CM은 관리 NIC에 RDMA 장치가 없어 연결하지 않는다. 일반 IP 트래픽은 관리망으로 나갈 수 있다. 막으려면 netplan `ignore-carrier: true`로 주소를 유지하거나 실습망에 unreachable 경로를 두는 방법이 있다. 어느 쪽도 이번에는 적용하지 않았다.

**버전 고정의 비용.** `common` 역할은 lock의 정확한 버전을 설치한다. noble-updates가 rdma-core를 올리면 이전 버전이 색인에서 빠지고 `make bootstrap`은 실패한다. 실패 메시지가 원인을 말하며, 다시 probe하고 lock을 고정해야 한다.

## 7. 정리와 초기화

러너를 SIGKILL로 죽이면 worker1에는 tcpdump 두 개와 기다리던 `ib_read_bw` 서버가 `timeout`·`sh` 래퍼와 함께 9개 프로세스로 남았다. worker2에도 캡처가 남았다(`30-leftovers-before-cleanup.log`). 다른 run id를 가진 미끼 `sleep 900`도 함께 있었다.

`make cleanup RUN=20261115T022855Z`는 그 run의 프로세스만 멈추고 `/var/tmp/rfl/20261115T022855Z`만 지웠다(`31`). 그 뒤에도 미끼 프로세스와 그 디렉터리, 두 worker의 `rxe0`가 남아 있었고 게스트는 계속 돌았다(`32`, `33`). 미끼는 `make cleanup RUN=20991231T235959Z`로 따로 지웠다(`34`).

## 9. M2 전제 조건

- `make doctor`가 0이고 `make versions SCOPE=m1`이 0이다.
- 두 worker에서 `make preflight`와 `make rxe-test`가 통과한 상태다. M2 이후에도 같은 시나리오로 회귀를 확인한다.
- `cp1` 게스트가 필요하다. 하네스의 `guests.tsv`에 RDMA NIC 없는 행을 추가하거나 VMware에서 만든다. 하네스의 관리망은 게스트마다 분리돼 있으므로, Kubernetes를 올리려면 세 게스트가 공유하는 관리망을 먼저 하네스에 추가해야 한다.
- kubelet Node IP와 API advertise address를 관리 IP로 명시한다. lab NIC 링크가 내려가면 lab 주소가 사라진다는 6절의 동작을 Node IP 선택에서 고려한다.
- `k8s.*`, `cni.cilium_chart`를 lock에 고정해 `make versions SCOPE=m2`가 0이 되게 한다.
- 6절의 관리망 누출 경로를 어떻게 다룰지 정한다.
