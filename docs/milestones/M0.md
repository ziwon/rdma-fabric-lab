# M0 — 설계 잠금

> 수행일: 2026-11-15  
> 판정: **통과.** CIDR 충돌 검사, 가상화 지원, RXE 사전 조건을 이 호스트에서 실행으로 확인했다.  
> 실행 환경: Ubuntu 24.04.5 LTS 호스트, 커널 7.0.0-42-generic. VMware Workstation은 없다. 게스트는 비특권 QEMU/KVM(`qemu-system-x86 1:8.2.2+ds-0ubuntu1.18`)으로 띄웠다.

관리 NIC와 RDMA NIC 이름은 추적되는 inventory에 없다. 하이퍼바이저마다 다르기 때문이다. QEMU 하네스는 게스트 안에서 MAC으로 이름을 찾아 `.lab/inventory.yml`에 쓰고, 모든 lab target은 이 파일을 `ansible/inventories/lab/` 뒤의 두 번째 `-i`로 쓴다. VMware 경로는 `docs/setup-vmware.md` 6절을 따른다.

## 2. 주소 계획과 호스트

`make doctor`는 호스트를 바꾸지 않는다. 다음 네 곳에서 범위를 읽고 주소 계획의 다섯 범위와 겹치는지 본다.

| 출처 | 명령 |
|---|---|
| 인터페이스 주소 | `ip -j addr show` |
| 모든 라우팅 테이블, IPv4·IPv6 | `ip -j route show table all` |
| docker 네트워크 | `docker network ls -q`, `docker network inspect` |
| libvirt 네트워크 | `virsh -c qemu:///system net-list --all`, `net-dumpxml` |

이 호스트에서 doctor가 스스로 찾은 IPv4 범위에는 `172.16.0.0/24`, `172.17.0.0/16`부터 `172.24.0.0/16`까지의 docker bridge, `192.168.122.0/24` libvirt, `10.42.0.0/24` Cilium, `100.64.0.0/10` 안의 Tailscale `/32` 주소와 라우트가 있다. 링크가 내려간 docker bridge도 포함된다. PLAN 3.2 계획은 이 중 어느 것과도 겹치지 않는다.

계획을 `docker0`과 겹치게 바꾸면(`rdma: 172.17.0.0/24`) doctor는 주소, 연결 라우트, local 라우트, docker 네트워크와의 겹침을 각각 `[fail]`로 출력하고 종료 코드 1을 낸다. 노드 RDMA 주소가 새 RDMA망 밖에 있다는 계획 내부 모순도 함께 출력한다.

## 3. 실행한 명령과 결과

모든 로그는 `.lab/acceptance/20261115T022117Z/` 아래에 있다. 이 디렉터리는 gitignore 대상이며 이 호스트에 남겼다. 단계별 종료 코드는 `docs/milestones/evidence/m1/acceptance-steps.tsv`에 복사했다.

| 단계 | 명령 | 종료 코드 | 로그 |
|---|---|---:|---|
| 하네스 정지 | `make lab-down` | 0 | `01-lab-down.log` |
| 게스트 디스크 삭제 | `make lab-wipe` | 0 | `02-lab-wipe.log` |
| 게스트 두 대 기동 | `make lab-up` | 0 | `03-lab-up.log` |

`make`는 recipe가 실패하면 자기 종료 코드 2를 낸다. 괄호 안은 recipe가 낸 값이다.

doctor의 경고는 하나다. 저장소 파일시스템의 여유 공간 34GiB가 PLAN 3.1의 VM 디스크 예산 110GiB보다 작다. QEMU qcow2 overlay는 쓰는 만큼만 커지므로 M1 실행에는 문제가 없었다. 미리 할당한 VMware 디스크라면 부족하다.

bootstrap 전 사전 검사는 의도대로 실패했다. RDMA NIC에 주소가 없고, `rdma_rxe` 모듈이 없고, lock의 패키지가 설치되지 않았다는 원인을 항목별로 출력했다.

## 4. RXE 사전 조건 probe

M1을 쌓기 전에 가장 불확실한 세 가지를 실제 게스트에서 확인했다. 로그는 `docs/milestones/evidence/m1/probe.log`와 `probe-fault.txt`다. 원본은 `.lab/probe/20261115T012426Z/`다.

| 질문 | 관찰 |
|---|---|
| 게스트 커널에 `rdma_rxe`가 있는가 | 20261017 이미지의 6.8.0-147-generic에는 없다. `linux-modules-extra-6.8.0-147-generic`(noble-updates, noble-security)이 `rdma_rxe.ko.zst`를 제공한다 |
| 두 번째 NIC가 호스트 밖으로 나가지 않고 두 게스트 사이에 프레임을 전달하는가 | `-netdev dgram`을 AF_UNIX 소켓 두 개로 연결했다. ping 3/3, 이웃 항목에 상대 실습 NIC MAC `52:54:00:4d:00:12`가 있다 |
| `rdma link add`가 그 NIC에 붙고 `rping`이 완료되는가 | `rxe0`가 `enp0s4`에 ACTIVE로 붙었다. `rping -C 5 -V`가 양쪽 종료 코드 0으로 끝났다 |

세 질문 모두 "예"였으므로 M1을 진행했다.

## 5. 버전 lock

`make versions SCOPE=m1`이 0으로 끝난다. `make bootstrap`, `make rxe-up`, `make rxe-test`, `make preflight`, `make collect`는 이 검사에 의존한다.

| component | 값 | 출처 |
|---|---|---|
| `lab.guest_image` | `sha256:04e8f246…6c94`, ref `noble/20261017` | GPG 서명을 확인한 `SHA256SUMS` |
| `lab.guest_os` | Ubuntu 24.04.5 LTS | 게스트의 `/etc/os-release` |
| `lab.guest_kernel` | 6.8.0-147-generic | 게스트의 `uname -r` |
| `lab.rdma_core` | 50.0-2ubuntu0.2 | 게스트의 `apt-cache policy` |
| `lab.perftest` | 24.01.0+0.38-1build2 | 게스트의 `apt-cache policy` |
| `host.os`, `host.kernel`, `host.hypervisor` | Ubuntu 24.04.5 LTS, 7.0.0-42-generic, qemu-system-x86 1:8.2.2+ds-0ubuntu1.18 with KVM | 호스트 |

게스트가 보고하는 값과 lock이 일치하는지는 M1의 `make collect`가 확인한다.

## 6. 다음 단계 전제 조건

M1의 전제 조건은 이 문서로 충족됐다. M2(Kubernetes)의 전제 조건은 M1 문서 7절에 있다. M0에서 M2로 넘기는 것은 다음과 같다.

- Pod CIDR `10.244.0.0/16`과 Service CIDR `10.96.0.0/12`는 이 호스트의 어느 범위와도 겹치지 않는다. 다른 호스트에서는 `make doctor`를 다시 실행한다.
- `k8s.*`, `cni.cilium_chart`는 lock에서 아직 `null`이다. M2 시작 전에 `make versions SCOPE=m2`가 0이 되도록 고정한다.
- `cp1`은 inventory에만 있고 하네스는 띄우지 않는다. M2는 `cp1`을 하네스에 추가하거나 VMware에서 만든다.
