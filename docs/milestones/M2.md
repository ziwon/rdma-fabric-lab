## 3. How the harness differs from the VMware network design

| Item | VMware network design | QEMU harness |
|---|---|---|
| Management network | One NAT VMnet carries internet, SSH and the Kubernetes API | Split in two. A QEMU user NIC per guest (`10.0.2.0/24`, DHCP, default route, SSH and package downloads), and a management network the three guests share (`192.168.140.0/24`, static addresses, Kubernetes and VXLAN) |
| Management network L2 | VMware virtual switch | `switch.py`. A Python learning switch with user privileges moves frames over AF_UNIX datagram sockets. Frames cannot leave the host, and the process has no capabilities (`CapEff: 0000000000000000`) |
| Management address setup | Set during VM installation | cloud-init network-config sets it at first boot. Ansible does not touch the management NIC |
| Default route and SSH | Management NIC | User NIC. The inventory variable `lab_uplink_nic` points at this NIC. It is not set for VMware |
| API from the host | Reaches `192.168.140.11:6443` through the host adapter of the NAT VMnet | Not reachable. Port 6443 of cp1 is forwarded to `127.0.0.1:22643`, and `make k8s` sets the server of the fetched kubeconfig to that address and `tls-server-name` to `kubernetes` |
| RDMA lab network | host-only VMnet | The same direct worker1–worker2 dgram socket pair as in M1 |
| NIC names | Names checked after installation (`ens33` and others) | Found by MAC and written to the override inventory. When a profile declares a name, the first boot renames the NIC to it and no variable is used (`mgmt0` in the ha profile) |
| Guest size | cp1 2 vCPU 4 GiB, worker 4 vCPU 6 GiB | The same. The ha profile uses 2 vCPU, 2.5 GiB per control plane and 2 GiB for the worker |
| Power failure | Power off the VM | `lab.sh kill`. It sends SIGKILL to QEMU and cuts the guest off without its shutdown sequence |

## 4. Behavior

**containerd role.** It downloads the three release files to `/var/cache/rfl/k8s` with `get_url`, passing the sha256 from the lock. Any other bytes are rejected. containerd unpacks into `/usr/local`, CNI plugins into `/opt/cni/bin`, and runc goes to `/usr/local/sbin/runc`. The configuration is version 4, which containerd 2.4 uses, and it runs runc with the systemd cgroup driver. If the same file already exists, the role does not change it. `kubernetes-cni` 1.9.1-1.1, which the kubelet package depends on, unpacks plugins of a different release into `/opt/cni/bin`. So the role first sets the dpkg `path-exclude=/opt/cni/bin/*`. After installation, `loopback` reported v1.10.0.

**kubeadm role.** Before it changes anything, the play checks the contract of every host. The first control plane runs `kubeadm init --skip-token-print` with the rendered `/etc/kubernetes/rfl/kubeadm-init.yaml` (v1beta4). The configuration holds the endpoint, the Pod and Service CIDRs, `node-ip`, `node-labels` and the kube-proxy choice. The other control planes join with a fresh 15-minute token from the first node and the certificate key uploaded with `upload-certs`. The join configuration that holds the token and key is deleted right after the join. Tasks that handle the token or key are `no_log`. init and join run only when `/etc/kubernetes/admin.conf` and `kubelet.conf` do not exist. On a rerun, the role stops if the stored kubeadm-config differs from the inventory. It does not reconfigure or upgrade.

**kube-vip.** When `k8s_api_vip` is set, every control plane gets a static pod. The image is pinned by tag and OCI index digest. In ARP mode, the lease `plndr-cp-lock` (5 seconds) lets only one node hold the VIP. The first node uses `super-admin.conf` until init finishes and then switches to `admin.conf`, because since Kubernetes 1.29 the permissions of `admin.conf` appear only partway through init. An inventory without a VIP gets the static pod file deleted.

**kubeconfig.** The admin.conf of the first control plane is written to `k8s_admin_kubeconfig` (for the lab, `.lab/kubeconfig` relative to the repository) with mode 0600. Without the variable, the path is `${XDG_STATE_HOME:-~/.local/state}/rdma-fabric-lab/<rfl_inventory>/kubeconfig` from ADR section 5.

**Cilium.** `make addons ENV=lab KUBECONFIG_FILE=.lab/kubeconfig` installs it as `helm/releases.yaml` lists. All five keys of the values file exist in the values.yaml of the 1.20.4 chart (`make values-check ENV=lab`: 0 unknown keys). The rendered `cilium-config` has `routing-mode: tunnel`, `tunnel-protocol: vxlan`, `ipam: kubernetes`, `kube-proxy-replacement: false` and `cni-exclusive: false`. The VXLAN port is the chart default 8472, and the runner reads this value from the `cilium_vxlan` device of the node.

**Skipping reinstalls.** `helm upgrade --install` writes a new revision even when the values are the same. So `make addons` first reads `helm get metadata` and `helm get values`. When the status is deployed and the chart version and user values are the same, it prints `cilium: unchanged` and skips. The values merge follows `MergeMaps` of Helm v4.3.2. Maps merge key by key, and lists and scalars of a later file replace the earlier value. A null in a later file stays in the stored user values as a null key and removes the chart default at render time. A real release confirmed this (`evidence/m2/helm-null-probe.txt`: `get values` returns `{"a":5,"b":null,"l":["x"]}`, and the rendered values are `{"a":5,"l":["x"]}`). A skip leaves drifted objects unrepaired by Helm, so `FORCE=1` exists.

## 9. Findings

**A restarted Cilium agent could not reach the API.** In the first M2 acceptance test (`.lab/acceptance-m2/20261115T053321Z`), after the agent pod on worker1 was deleted, the init container `config` of the new pod kept dying with `dial tcp 10.96.0.1:443: i/o timeout`. At first installation the same path worked. The cause was three conditions together.

- In the harness, the default route is on the user NIC. So a connection from the host to a ClusterIP picks `10.0.2.15` as its source address.
- Normally kube-proxy puts a masquerade mark on this connection and rewrites it to the address of the management NIC. But the agent's socket carried `fwmark:0x10b00` (`ss -tnpei`). Cilium's `CILIUM_POST_nat` treats the `0xa00/0xe00` mark as "proxy return traffic" and ACCEPTs it before the kube-proxy rules. The SYN left through the management NIC still carrying `10.0.2.15` (`tcpdump`), and the reply from cp1 vanished through cp1's own user NIC. The MASQUERADE counter in `KUBE-POSTROUTING` was 0.
- At first installation, `CILIUM_POST_nat` did not exist yet, so kube-proxy rewrote the address.

The ha profile reproduced this with Cilium switched back to the ClusterIP path (`evidence/m2/cilium-rootcause/`). The Helm upgrade timed out at `Available: 3/4`. The three control planes, which have the API on their own node, came up. Only the worker ha-w1 failed. On ha-w1 the `cilium-dbg` socket had `fwmark:0x10b00`, the SYN left through `mgmt0` carrying `10.0.2.15`, and the `KUBE-POSTROUTING` MASQUERADE counter was 0. With the values file restored, all four agents were Running.

On the same host, `curl https://10.96.0.1` returned 200, so a routing problem was ruled out. The pod was scheduled and its init container died, so a scheduler problem was ruled out too. The fix makes Cilium go directly to the API address instead of the ClusterIP. The kubeadm role writes the contract variables `k8s_api_endpoint` and `k8s_api_port` to the `kube-system/rfl-api-endpoint` ConfigMap, and `k8sServiceHostRef` in `values-lab.yaml` reads it. `k8sServiceHost: auto` was not chosen, because it uses Helm `lookup`, which makes the offline `make addons-template` fail. Writing the address into the values file was not chosen either, because it would break the ha profile, which uses the same `lab` environment. After the fix, all three agents came up again on the running cluster, and `k8s-baseline` passed (run `20261115T055930Z`). Fleet nodes whose default route and node IP sit on different NICs have the same condition. Whether `values-cel1.yaml` needs the same setting was handed to the coordinator.

**`kubernetes-cni` overwrites the CNI plugins.** kubelet 1.36.6-1.1 depends on `kubernetes-cni` (>= 1.2.0), and 1.9.1-1.1 from pkgs.k8s.io unpacks its own plugins into `/opt/cni/bin`. To keep the locked v1.10.0, the containerd role sets a dpkg `path-exclude`. After installation, `dpkg -L kubernetes-cni` shows the file list, but `/opt/cni/bin/loopback` is v1.10.0.

**`kubeadm init phase upload-certs` needs `--config`.** Without it, kubeadm used the default configuration, looked up the version online (`remote version is much newer: v1.37.2`), and failed after 60 seconds while creating the admin ClusterRoleBinding. The first ha attempt stopped for this reason (`.lab/m2/ha-k8s-1.log`). With the rendered init configuration passed in, it finished in 0.06 seconds. VIP flapping and API latency were ruled out. The lease and the VIP stayed on ha-cp1 the whole time, and the same API answered at once. `kubeadm token create` stays as it is, because it cannot mix `--config` with other flags. This command takes about 12 seconds because of the version lookup.

**The configuration version of containerd 2.4.2 is 4.** A version 3 file leaves the warning `Configuration migrated from version 3`. The role writes version 4.

**`helm upgrade --install` always bumps the revision.** It does so even when the values are the same. So `make addons` compares with the deployed values and skips (section 4).

**The pkgs.k8s.io signing key expires on 2026-12-29.** The role pins the key fingerprint and checks it. When the key changes, `make k8s` stops, so the new fingerprint must be verified and `kubeadm_apt_key_fingerprint` updated.

**Cilium agent readiness does not notice a VXLAN fault.** With UDP 8472 dropped on worker1, all three agents were still ready. The traffic checks and the capture checks catch the fault.

**The API VIP gap was 6 to 9 seconds.** The four measured values are 6.031, 7.538, 9.04 and 9.045 seconds. The gap runs from the power cut until the lease (5 seconds) expires and the new node announces the VIP by ARP. The measurement uses probes at 0.5-second intervals, so it can read short by one interval.

- A lab profile cluster on which `make k8s`, `make addons ENV=lab KUBECONFIG_FILE=.lab/kubeconfig` and `make k8s-test` passed. A rerun must report `changed=0` and `cilium: unchanged`.
- `vm-rxe-baseline` passing on guests with Kubernetes running. The M3 hostNetwork RDMA pods compare against this baseline.
- Cilium with `cni.exclusive: false` kept. Multus takes `05-cilium.conflist` in `/etc/cni/net.d` as its default delegate.
- macvlan and ipvlan in `/opt/cni/bin` come from CNI plugins v1.10.0. The dpkg `path-exclude` guards that location.
- The Whereabouts and Multus versions (`cni.multus`, `cni.whereabouts`) are in the lock. Check them with `make versions SCOPE=m3`.
- The master of the Multus secondary network is the worker's `lab_rdma_nic`. The harness lab network is a dgram socket pair, so M3 first checks whether the extra macvlan MACs get through.
- The workers have RXE devices, and the Kubernetes scenarios and the RXE scenarios pass together on the same guests. Alternating the two catches regressions.
