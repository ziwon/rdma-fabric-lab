## 3. 하네스와 PLAN 3.2 VMware 구성의 차이

| 항목 | PLAN 3.2 VMware | QEMU 하네스 |
|---|---|---|
| 관리망 | NAT VMnet 하나가 인터넷, SSH, Kubernetes API를 모두 나른다 | 둘로 나눴다. 게스트마다 QEMU user NIC(`10.0.2.0/24`, DHCP, 기본 경로, SSH와 패키지 내려받기)와, 세 게스트가 공유하는 관리망(`192.168.140.0/24`, 고정 주소, Kubernetes와 VXLAN) |
| 관리망 L2 | VMware 가상 스위치 | `switch.py`. 사용자 권한의 Python 학습 스위치가 AF_UNIX datagram 소켓으로 프레임을 옮긴다. 프레임은 호스트를 떠날 수 없고 프로세스에 capability가 없다(`CapEff: 0000000000000000`) |
| 관리 주소 설정 | VM 설치 때 정한다 | cloud-init network-config가 첫 부팅에 넣는다. Ansible은 관리 NIC를 건드리지 않는다 |
| 기본 경로와 SSH | 관리 NIC | user NIC. 인벤토리 변수 `lab_uplink_nic`이 이 NIC를 가리킨다. VMware에서는 두지 않는다 |
| 호스트에서 API | NAT VMnet의 호스트 어댑터로 `192.168.140.11:6443`에 닿는다 | 닿지 않는다. cp1의 6443을 `127.0.0.1:22643`으로 전달하고, `make k8s`가 가져온 kubeconfig의 server를 그 주소로, `tls-server-name`을 `kubernetes`로 바꾼다 |
| RDMA 실습망 | host-only VMnet | M1과 같은 worker1–worker2 직결 dgram 소켓 쌍 |
| NIC 이름 | 설치 후 확인한 이름(`ens33` 등) | MAC으로 찾아 override 인벤토리에 쓴다. 프로필이 이름을 선언하면 첫 부팅에 그 이름으로 바꾸고 변수를 쓰지 않는다(ha 프로필의 `mgmt0`) |
| 게스트 크기 | cp1 2 vCPU 4 GiB, worker 4 vCPU 6 GiB | 같다. ha 프로필은 2 vCPU, 컨트롤 플레인 2.5 GiB, 워커 2 GiB |
| 전원 장애 | VM 끄기 | `lab.sh kill`. QEMU에 SIGKILL을 보내 게스트 안의 종료 절차 없이 끊는다 |

## 4. 동작

**containerd 역할.** 세 릴리스 파일을 `get_url`에 lock의 sha256을 주어 `/var/cache/rfl/k8s`에 받는다. 다른 바이트는 거부된다. containerd는 `/usr/local`, CNI plugins는 `/opt/cni/bin`에 풀고 runc는 `/usr/local/sbin/runc`에 둔다. 설정은 containerd 2.4가 쓰는 version 4이고, runc를 systemd cgroup 드라이버로 돌린다. 같은 파일이 이미 있으면 바꾸지 않는다. kubelet 패키지가 의존하는 `kubernetes-cni` 1.9.1-1.1은 `/opt/cni/bin`에 다른 릴리스의 플러그인을 풀기 때문에, 역할이 먼저 dpkg `path-exclude=/opt/cni/bin/*`를 둔다. 설치 뒤 `loopback`은 v1.10.0을 보고했다.

**kubeadm 역할.** 플레이는 아무것도 바꾸기 전에 모든 호스트의 계약을 검사한다. 첫 컨트롤 플레인은 렌더한 `/etc/kubernetes/rfl/kubeadm-init.yaml`(v1beta4)로 `kubeadm init --skip-token-print`를 한다. 설정에는 endpoint, Pod·Service CIDR, `node-ip`, `node-labels`, kube-proxy 선택이 들어간다. 다른 컨트롤 플레인은 첫 노드에서 새로 만든 15분짜리 토큰과 `upload-certs`로 올린 인증서 키로 join한다. 토큰과 키를 담은 join 설정은 join 직후 지운다. 토큰·키를 다루는 태스크는 `no_log`다. init·join은 `/etc/kubernetes/admin.conf`, `kubelet.conf`가 없을 때만 실행한다. 재실행 때는 저장된 kubeadm-config가 인벤토리와 다르면 멈춘다. 재구성과 업그레이드는 하지 않는다.

**kube-vip.** `k8s_api_vip`가 있으면 모든 컨트롤 플레인에 static pod를 둔다. 이미지는 태그와 OCI index digest로 고정한다. ARP 모드, lease `plndr-cp-lock`(5초)으로 한 노드만 VIP를 갖는다. 첫 노드는 init이 끝날 때까지 `super-admin.conf`를 쓰고 그다음 `admin.conf`로 바꾼다. Kubernetes 1.29부터 `admin.conf`의 권한은 init 중간에야 생기기 때문이다. VIP가 없는 인벤토리에서는 static pod 파일을 지운다.

**kubeconfig.** 첫 컨트롤 플레인의 admin.conf를 `k8s_admin_kubeconfig`(랩은 저장소 기준 `.lab/kubeconfig`)에 권한 0600으로 쓴다. 변수가 없으면 ADR 5절의 `${XDG_STATE_HOME:-~/.local/state}/rdma-fabric-lab/<rfl_inventory>/kubeconfig`다.

**Cilium.** `make addons ENV=lab KUBECONFIG_FILE=.lab/kubeconfig`가 `helm/releases.yaml`대로 설치한다. 값 파일의 다섯 키는 1.20.4 chart의 values.yaml에 모두 있다(`make values-check ENV=lab`: 0 unknown keys). 렌더한 `cilium-config`는 `routing-mode: tunnel`, `tunnel-protocol: vxlan`, `ipam: kubernetes`, `kube-proxy-replacement: false`, `cni-exclusive: false`다. VXLAN 포트는 chart 기본값인 8472이고, 러너는 이 값을 노드의 `cilium_vxlan` 장치에서 읽는다.

**재설치 건너뛰기.** `helm upgrade --install`은 값이 같아도 새 revision을 쓴다. 그래서 `make addons`는 `helm get metadata`, `helm get values`를 먼저 읽는다. 상태가 deployed이고 chart 버전과 사용자 값이 같으면 `cilium: unchanged`를 출력하고 건너뛴다. 값 병합은 Helm v4.3.2의 `MergeMaps`를 따른다. 맵은 키별로 합치고, 뒤 파일의 목록과 스칼라는 앞 값을 바꾼다. 뒤 파일의 null은 저장된 사용자 값에 null 키로 남고, 렌더할 때 chart 기본값을 지운다. 실제 릴리스로 확인했다(`evidence/m2/helm-null-probe.txt`: `get values`는 `{"a":5,"b":null,"l":["x"]}`, 렌더 값은 `{"a":5,"l":["x"]}`). 건너뛰면 Helm이 어긋난 객체를 고치지 않으므로 `FORCE=1`을 둔다.

## 8. nvidia 기본 런타임

`k8s_container_runtime_default: nvidia`를 버릴 게스트 ha-w1에만 임시 인벤토리로 주고 `make k8s LAB_PROFILE=ha`를 돌렸다. ha-w1만 `changed=2`였다. 역할은 `/usr/bin/nvidia-container-runtime`이 없다고 경고했다. `containerd config dump`에는 `default_runtime_name = 'nvidia'`와 `runtimes.nvidia`의 `BinaryName = '/usr/bin/nvidia-container-runtime'`이 있었다(`evidence/m2/nvidia-probe/dump-nvidia.txt`). 임시 인벤토리 없이 다시 돌리자 ha-w1이 `changed=2`로 `default_runtime_name = 'runc'`로 돌아갔고(`dump-reverted.txt`), 네 노드가 모두 Ready였다. 이 게스트에서는 Kubernetes 시나리오를 돌리지 않았다. 바이너리가 없어 새 컨테이너가 뜨지 않기 때문이다.

## 9. 발견 사항

**재시작한 Cilium agent가 API에 닿지 못했다.** 처음 M2 인수 시험(`.lab/acceptance-m2/20261115T053321Z`)에서 worker1의 agent pod를 지우자 새 pod의 init 컨테이너 `config`가 `dial tcp 10.96.0.1:443: i/o timeout`으로 계속 죽었다. 첫 설치 때는 같은 경로가 됐다. 원인은 세 가지가 겹친 것이다.

- 하네스에서는 기본 경로가 user NIC에 있다. 그래서 호스트에서 ClusterIP로 가는 연결은 출발 주소로 `10.0.2.15`를 고른다.
- 보통은 kube-proxy가 이 연결에 masquerade 표식을 달아 관리 NIC의 주소로 바꾼다. 그런데 agent의 소켓에는 `fwmark:0x10b00`이 붙어 있었다(`ss -tnpei`). Cilium의 `CILIUM_POST_nat`은 `0xa00/0xe00` 표식을 "proxy return traffic"으로 보고 kube-proxy 규칙보다 먼저 ACCEPT한다. SYN은 `10.0.2.15`를 단 채 관리 NIC로 나갔고(`tcpdump`), cp1의 응답은 cp1 자신의 user NIC로 사라졌다. `KUBE-POSTROUTING`의 MASQUERADE 계수는 0이었다.
- 첫 설치 때는 `CILIUM_POST_nat`이 아직 없어서 kube-proxy가 주소를 바꿨다.

ha 프로필에서 Cilium을 ClusterIP 경로로 되돌려 재현했다(`evidence/m2/cilium-rootcause/`). Helm upgrade는 `Available: 3/4`에서 시간이 다 됐다. API가 자기 노드에 있는 세 컨트롤 플레인은 떴고 워커 ha-w1만 실패했다. ha-w1의 `cilium-dbg` 소켓은 `fwmark:0x10b00`, SYN은 `mgmt0`으로 `10.0.2.15`를 단 채 나갔고 `KUBE-POSTROUTING` MASQUERADE 계수는 0이었다. 값 파일을 되돌리자 네 agent가 모두 Running이었다.

같은 호스트에서 `curl https://10.96.0.1`은 200이었으므로 경로 문제는 기각했다. pod는 스케줄됐고 init 컨테이너가 죽었으므로 스케줄러 문제도 기각했다. 고친 방법은 Cilium이 ClusterIP 대신 API 주소로 직접 가게 한 것이다. kubeadm 역할이 계약의 `k8s_api_endpoint`·`k8s_api_port`를 `kube-system/rfl-api-endpoint` ConfigMap에 쓰고, `values-lab.yaml`의 `k8sServiceHostRef`가 그것을 읽는다. `k8sServiceHost: auto`는 Helm `lookup`을 써서 오프라인 `make addons-template`이 실패하고, 주소를 값 파일에 쓰면 같은 `lab` 환경을 쓰는 ha 프로필이 깨지므로 고르지 않았다. 고친 뒤 살아 있던 클러스터에서 세 agent가 모두 다시 떴고 `k8s-baseline`이 통과했다(run `20261115T055930Z`). 기본 경로와 노드 IP가 다른 NIC에 있는 플릿 노드도 같은 조건이다. `values-cel1.yaml`에도 같은 설정이 필요한지는 코디네이터에게 넘겼다.

**`kubernetes-cni`가 CNI plugins를 덮어쓴다.** kubelet 1.36.6-1.1은 `kubernetes-cni`(>= 1.2.0)에 의존하고, pkgs.k8s.io의 1.9.1-1.1은 `/opt/cni/bin`에 자기 플러그인을 푼다. lock의 v1.10.0을 지키려고 containerd 역할이 dpkg `path-exclude`를 둔다. 설치 뒤 `dpkg -L kubernetes-cni`는 파일 목록을 보여 주지만 `/opt/cni/bin/loopback`은 v1.10.0이다.

**`kubeadm init phase upload-certs`는 `--config`가 필요하다.** 없이 실행하면 kubeadm이 기본 설정으로 온라인에서 버전을 찾고(`remote version is much newer: v1.37.2`) admin ClusterRoleBinding을 만들다 60초 뒤 실패했다. 첫 ha 시도가 이 이유로 멈췄다(`.lab/m2/ha-k8s-1.log`). 렌더한 init 설정을 넘기자 0.06초에 끝났다. VIP 흔들림과 API 지연은 기각했다. lease와 VIP는 내내 ha-cp1에 있었고 같은 API가 바로 답했다. `kubeadm token create`는 `--config`를 다른 플래그와 섞을 수 없어 그대로 둔다. 이 명령은 버전 조회 때문에 12초쯤 걸린다.

**containerd 2.4.2의 설정 버전은 4다.** version 3 파일을 쓰면 `Configuration migrated from version 3` 경고를 남긴다. 역할은 version 4를 쓴다.

**`helm upgrade --install`은 늘 revision을 올린다.** 값이 같아도 그렇다. 그래서 `make addons`가 배포된 값과 비교해 건너뛴다(4절).

**pkgs.k8s.io 서명 키는 2026-12-29에 만료된다.** 역할은 키 지문을 고정해 확인한다. 키가 바뀌면 `make k8s`가 멈추므로 새 지문을 확인하고 `kubeadm_apt_key_fingerprint`를 바꿔야 한다.

**Cilium agent의 준비 상태는 VXLAN 장애를 모른다.** worker1에서 UDP 8472를 버려도 세 agent는 ready였다. 장애는 트래픽 검사와 캡처 검사가 잡는다.

**API VIP 공백은 6–9초였다.** 네 번 잰 값이 6.031, 7.538, 9.04, 9.045초다. 전원을 끊은 시점부터 lease(5초)가 만료되고 새 노드가 VIP를 ARP로 알릴 때까지다. 측정은 0.5초 간격 probe라 한 간격만큼 짧게 잴 수 있다.

## 10. 실행하지 않은 것

- VMware Workstation 경로. 이 호스트에 없다. `docs/setup-vmware.md`에 M2 명령을 더했지만 검증하지 않았다.
- 플릿 하드웨어. 이 작업은 cel1 인벤토리로 아무것도 실행하지 않았다. 플레이북은 ha 프로필에서 세 컨트롤 플레인과 VIP 모양으로만 확인했다.
- 패키지 containerd(`containerd.io`)가 깔린 호스트에서 역할이 멈추는지. 그런 게스트를 만들지 않았다. 검사 코드만 있다.
- 실제 NVIDIA 컨테이너 툴킷이 있는 노드에서 nvidia 런타임으로 pod를 띄우는 것. 이 호스트에 GPU와 툴킷이 없다.
- swap이 켜진 호스트. 클라우드 이미지에는 swap이 없어 `swapoff` 태스크는 늘 건너뛰었다.
- kube-proxy 없는 구성(`k8s_kube_proxy: false`). 랩은 PLAN A2대로 kube-proxy를 쓴다.
- ha 프로필의 VXLAN·NetworkPolicy 시나리오. ha 프로필은 VIP 증명만 한다.

## 11. M3 전제 조건

- `make k8s`, `make addons ENV=lab KUBECONFIG_FILE=.lab/kubeconfig`, `make k8s-test`가 통과한 lab 프로필 클러스터. 재실행은 `changed=0`, `cilium: unchanged`여야 한다.
- `vm-rxe-baseline`이 Kubernetes가 올라간 게스트에서 통과한 상태. M3의 hostNetwork RDMA pod는 이 기준선과 비교한다.
- `cni.exclusive: false`가 유지된 Cilium. Multus는 `/etc/cni/net.d`의 `05-cilium.conflist`를 기본 delegate로 삼는다.
- `/opt/cni/bin`의 macvlan·ipvlan은 CNI plugins v1.10.0에서 온다. dpkg `path-exclude`가 그 자리를 지킨다.
- Whereabouts와 Multus 버전(`cni.multus`, `cni.whereabouts`)은 lock에 있다. `make versions SCOPE=m3`로 확인한다.
- Multus 보조망의 master는 worker의 `lab_rdma_nic`이다. 하네스의 실습망은 dgram 소켓 쌍이라 macvlan의 추가 MAC이 전달되는지 M3에서 먼저 확인한다.
- 워커에는 RXE 장치가 있고 Kubernetes 시나리오와 RXE 시나리오가 같은 게스트에서 함께 통과한다. 둘을 번갈아 돌려 회귀를 본다.
