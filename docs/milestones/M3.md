# M3: hostNetwork RDMA pods and the Multus secondary network

> Date: 2026-11-16  
> Verdict: **Both scenarios passed and validated from wiped guests.** `k8s-hostnet-rdma` repeated the M1 RXE baseline between hostNetwork pods (run `20261116T002950Z`), and `k8s-multus-net1` showed `net1` from Whereabouts beside Cilium, through pod recreation and a worker reboot (run `20261116T003040Z`). The M1 and M2 scenarios still pass on the same guests. Every check failed once on a deliberate break and passed after the repair. The pods need `privileged`. Multus left a window after each boot in which a new pod got no `net1` (section 9), and section 16 closes it: Cilium now writes its CNI file where only Multus reads it.  
> Environment: the lab profile of the QEMU harness (cp1, worker1, worker2), Ubuntu 24.04.5, kernel 6.8.0-147-generic, rdma-core 50.0-2ubuntu0.2, perftest 24.01.0+0.38-1build2, Kubernetes v1.36.6, Cilium chart 1.20.4, Multus v4.3.2 thick plugin, Whereabouts v0.9.4. Guest disks lived under `/data/rfl-lab/m3`. The host had 24 cores and 87 GiB of available memory before the first boot, and no other guest ran (`evidence/m3/host-before-boot.txt`).

M3 answers two questions with two scenarios and two verdicts.

1. `k8s-hostnet-rdma`: can a container on a worker use the node's RDMA device and repeat the M1 baseline? It can. This shows only that a container uses the node's device. It shows no pod-private interface, no device isolation and nothing about Cilium's pod data path.
2. `k8s-multus-net1`: can Multus add a secondary IP network `net1` beside Cilium, with cluster-wide Whereabouts addresses, without breaking the primary network? It can. `net1` is an IP network only. It carries no RDMA device, provider or permission into a pod.

## 4. Probes before building

**Extra MACs on the lab link pass.** `tests/integration/qemu-lab/probe-m3.sh macvlan` put one macvlan child in bridge mode on `lab0` of each worker, inside a throwaway network namespace, with one of the last two pool addresses. Each side sent 5 echo requests and got 5 replies. tcpdump on both lab NICs shows the frames with the children's own source MACs `42:37:32:85:de:21` and `86:74:87:7f:96:b9`, and `lab0` stayed at promiscuity 0, because virtio-net takes the extra MACs into its filter (`evidence/m3/probe-macvlan.log`). So macvlan stays the secondary type. ipvlan, the IP alternative, was not needed and did not run.

**RXE lists the addresses of macvlan children.** While the children existed, `rxe0` on each worker had two more GIDs, the IPv4-mapped child address and its link-local address, with `ndev` naming the child, although the child sat in another network namespace. They vanished with the children. M1 sets no GID index, so the M1 scenarios ran again with `net1` pods present (section 7). rdma_cm still chose GID index 1.

**Multus picks Cilium and sorts first.** After `make addons`, every node held `00-multus.conf` of type `multus-shim` with `clusterNetwork` `/host/etc/cni/net.d/05-cilium.conflist`, and it sorts before `05-cilium.conflist`. containerd loads the first file by name. `whereabouts.d` is a directory and no candidate (`evidence/m3/cni-netd-after-multus.txt`, before: `cni-netd-before-multus.txt`).

## 5. Pod security of the hostNetwork RDMA pods

Narrowest first. Each row is the error the narrower profile hit (`evidence/m3/pod-security-probe.txt`). The last row is the profile the scenario uses, and its `security` block says `privileged: true`.

| # | Profile | Result |
|---|---|---|
| 1 | Namespace at PodSecurity `restricted` | Refused at admission: `violates PodSecurity "restricted:latest": host namespaces (hostNetwork=true)` |
| 2 | Namespace at PodSecurity `baseline` | Refused at admission: `violates PodSecurity "baseline:latest": host namespaces (hostNetwork=true)`. hostNetwork needs the `privileged` level |
| 3 | `privileged` level, container uid 65534, all capabilities dropped, no privilege escalation, `RuntimeDefault` seccomp, no device | No `/dev/infiniband` in the container. sysfs lists `rxe0`. `ibv_devinfo`: `No IB devices found`, exit 255 |
| 4 | Profile 3 with `/dev/infiniband` as a hostPath | The files appear with mode 0666, but opening `uverbs0` and `rdma_cm` gives `Operation not permitted`: the device cgroup refuses them. `ibv_devinfo`: `Failed to open device`, exit 1. rping: `failed to create RDMA CM event channel` |
| 5 | `privileged: true`, uid and gid 65534, no hostPID, no host IPC, no volume, no runtime socket | `ibv_devinfo` shows `rxe0` `PORT_ACTIVE`. The process has no effective capability (`CapEff: 0000000000000000`). `ib_write_bw` 4096 B x 1000 completed between pods on worker1 and worker2 |

Kubernetes has no field that admits one character device to a container without a device plugin, and capabilities do not change the device cgroup. So profile 4 cannot work, and profile 5 is the narrowest that does. The user accepted `privileged` for the lab RDMA pods on 2026-11-16. A device plugin path that would remove it is the optional experiment after M3. Every run proves profiles 3 and 4 fail again in `narrower-profiles-fail`, and proves through a dry-run relabel that `baseline` and `restricted` would refuse both pods in `pod-security-as-declared`.

**memlock.** The pods run with 8388608 bytes soft and hard, the default of containerd's systemd service, which sets no `LimitMEMLOCK`. The node's SSH user that the VM baseline runs as has 776622080 bytes. No profile hit an `ibv_reg_mr` memlock error. With containerd's limit lowered to 65536 bytes on worker2 (break `memlock-64k-on-worker2`, run `20261115T225629Z`), rping and Read, Write and Send with 4096 B x 1000 still passed, so these test parameters register less than 64 KiB. `memlock-in-pods` records both limits and fails when the two ends differ.

## 6. The scenarios

**`k8s-hostnet-rdma`.** One pod per worker in `lab_k8s_namespace`, pinned by the `kubernetes.io/hostname` label, `hostNetwork: true`, `dnsPolicy: ClusterFirstWithHostNet`, image by digest with `imagePullPolicy: Never`, `RFL_RUN=<run-id>` in the container's environment. The pods sleep and the runner starts every process through `kubectl exec` on cp1, under `timeout`. rping and perftest take server, client, ports, sizes, iterations and time limits from `vm-rxe.yaml`, so the pods repeat `vm-rxe-baseline` unchanged against the lab NIC addresses. The server counts as ready when `rdma resource show cm_id` inside its pod shows the listener. tcpdump captures every NIC of both nodes over the SSH path, as in M1. At the end the namespace is deleted, and the node's `/proc` must hold no process with the run id, inside a pod or not. Each process's `<check>/<guest>-<role>.context.json` names node, pod, container, RDMA device, lab address and command.

**`k8s-multus-net1`.** The runner renders the NetworkAttachmentDefinition from the inventory alone: namespace `lab_k8s_namespace`, master `lab_rdma_nic`, which must be the same on every worker, and the Whereabouts `range`, `range_start` and `range_end` from `lab_address_plan.rdma` and `lab_address_plan.multus_pool`. A pool that leaves the lab network or holds a node's `lab_rdma_ip` is refused too. `python -m run.multus render` prints it:

```yaml
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: rdma-lab-net
  namespace: rdma-lab
spec:
  config: '{"cniVersion": "0.3.1", "name": "rdma-lab-net", "type": "macvlan", "master":
    "lab0", "mode": "bridge", "ipam": {"type": "whereabouts", "range": "10.77.0.0/24",
    "range_start": "10.77.0.100", "range_end": "10.77.0.199"}}'
```

With an extra inventory that gave worker2 `lab_rdma_nic: other0`, render stopped with exit 2: `lab_rdma_nic differs across the workers (worker1 lab0, worker2 other0). One NetworkAttachmentDefinition names one macvlan master for every node ...` (`evidence/m3/breaks-3/15-refuse-differing-lab-nics.log`). The test pods are busybox at the PodSecurity `restricted` level, with no host network. The server serves its pod name over HTTP. The client fetches it over eth0 and over net1, and the lab NIC of both workers is captured. Pod recreation deletes both pods, waits until Whereabouts holds nothing for them, and starts them again. The reboot check deletes the client, reboots worker2 through `systemctl reboot`, and waits until the Node reports the new boot ID and the Multus pod there started after the boot.

## 9. Findings

**Multus removes its file when it stops.** The thick daemon runs `os.Remove(multusConfigFile)` when its config watcher ends on SIGTERM (`pkg/server/config/manager.go` at v4.3.2). During the reboot of worker2 in run `20261115T221719Z`, `kubectl logs --previous` of the old Multus pod showed `caught terminated, stopping...` (that output was not kept), and after the boot `/etc/cni/net.d` held only `05-cilium.conflist` (`evidence/m3/runs/20261115T221719Z/.../reboot-keeps-cni-order/worker2-ls.txt`) until the new daemon wrote `00-multus.conf` 18 to 19 seconds after the boot. In that window containerd runs Cilium alone, so a pod started then gets eth0 and no net1, without an error. Run `20261116T053519Z` later showed exactly that for a pod created 6 s after a boot (section 16.2). The manifest has no readiness probe, so the Multus pod turns Ready before it writes the file. That first run read the directory at 22:19:33, less than a second before the file appeared at 22:19:34.103, and failed. The check then recorded the state at Multus Ready, waited up to `cni_settle_timeout_s` (60) for the settled order and recorded the gap as `reboot.multus_conf_absent_after_boot_s`. Section 16 moved Cilium's file to `/etc/cni/multus/net.d`, so in the window `/etc/cni/net.d` holds no CNI file, containerd has no network and new pods wait. `pod-at-boot-waits-for-multus` replaced that check and its measurement.

**Multus keeps the delegate it found at start.** With `multusConfigFile: auto`, the daemon takes the first CNI file it sees as the default delegate when it starts and only watches that file. A file that sorted before Cilium's at boot became the delegate. After that file was deleted, `00-multus.conf` still named it, the daemon logged `failed to get clusterNetwork` on every ADD and never regenerated, and every new pod on that node stayed in `ContainerCreating`. Restarting the Multus pod on that node regenerated the file with Cilium (`evidence/m3/shadow/`). Since section 16 the daemon takes its delegate from `/etc/cni/multus/net.d`, which only Cilium writes, so a stray file in `/etc/cni/net.d` can no longer become the delegate. The daemon still reads its own config only at start, and a change of its ConfigMap does not roll the DaemonSet, which is why `make cni-migrate` restarts it.

**A capture stopped right after the traffic lost its last packets.** In run `20261115T221719Z`, worker1's lab capture held 0 frames while worker2's held the 5 and 5 frames of the net1 request. libpcap without immediate mode hands packets to tcpdump in buffer-timeout batches, and worker1's capture was stopped within a second of the request. The Multus runner now uses `--immediate-mode`, and every later run saw both directions on both lab NICs.

**`make rxe-up` did not recreate a deleted device.** The oneshot `rfl-rxe.service` stays active, so `state: started` did nothing after `rdma link delete`. The role now reads the links after the unit settings and restarts the unit when the device is missing. A rerun on a healthy worker still reports `changed=0`.

**Whereabouts gives freed addresses back.** After pod deletion released `10.77.0.100` and `10.77.0.101`, the recreated pods got the same two addresses, which they could not have if the old allocations had leaked.

**Multus `default-route` selection did not move the default route.** A pod whose network selection asked for `default-route` through the lab network kept its default route on eth0, with and without a gateway in the IPAM configuration. The break for `default-route-on-eth0` therefore uses IPAM routes, and the check also asks the kernel which interface reaches the first control plane's node address.

**`ENV=lab` now installs Multus and Whereabouts on the ha profile too.** The ha acceptance run installed all three releases at revision 1 and still passed (section 7).

It would still rename every other file in `/etc/cni/multus/net.d`, which is also Multus's `confDir`, where it looks up the configuration of a network named by file or of a NetworkAttachmentDefinition without `spec.config` (`pkg/k8sclient/k8sclient.go` at v4.3.2). So it stays `false`. The chart rolls the agents on a config change only with `rollOutCiliumPods`, so the setting took effect only after the restart (`evidence/m3-cni-dir/probe/09-exclusive-true/`). The probe was reverted with `make addons ... RELEASE=cilium` and another agent restart.

### 16.5 The checks

| Check | Before | Now |
|---|---|---|
| `cni-dir-holds-only-multus` | `multus-config-first`: `00-multus.conf` sorts first, and its delegate runs cilium-cni | On every node `00-multus.conf` is the only CNI file of `/etc/cni/net.d`, its `clusterNetwork` is `05-cilium.conflist` in the `cni.confPath` of the Cilium values, and that file runs cilium-cni |
| `pod-at-boot-waits-for-multus` | `reboot-keeps-cni-order`: after the reboot, wait until `00-multus.conf` is first again, and record the gap | The worker reboots. As soon as the new boot answers SSH, a client pod that tolerates every NoSchedule taint is created there, as the Multus DaemonSet tolerates them. Then the runner samples containerd's NetworkReady and the CNI directory every half second while `00-multus.conf` is absent. Every sample must show no network, the pod's first `RunPodSandbox` must come after the file's birth time, the pod must get eth0 and net1, and the node's layout must hold afterwards |
| `new-pod-after-reboot-gets-net1` | Starts a new pod after the reboot | The pod created at boot holds its pool address once and reaches the server over net1 |

The pod tolerates the taints so that only the container runtime can hold it. Without the tolerations the scheduler holds it, and the check would pass with Cilium's file back in place (probe 3). Each sample reads NetworkReady first and lists the directory second. A listing without `00-multus.conf` shows the read before it saw no Multus file either. A sample whose listing holds the file straddled its write and does not count. Run `20261116T061046Z` failed on one such sample before the runner knew this (section 16.8).

The first run, `20261116T053228Z` on the probe cluster, passed all 14 checks. The pod was created by boot+5.8 s, containerd had no network in all 25 samples, Multus wrote its file at boot+18.5 s, and the sandbox began at boot+20.1 s.

### 16.6 Existing clusters: `make cni-migrate`

A cluster built before the change keeps `05-cilium.conflist` in `/etc/cni/net.d`, because Cilium never removes it (`cni.uninstall: false`). And `make addons` alone does not restart Multus: the daemon config is a ConfigMap, the daemon reads it only at start, and a ConfigMap change does not roll the DaemonSet. `make cni-migrate` runs `ansible/playbooks/cni-migrate.yml`, which applies the role `cni_layout` to every node of `k8s_cluster`, one at a time.

1. Refuse, and change nothing, unless the cluster's `multus-daemon-config` takes its delegate from Cilium's directory and the node holds Cilium's file there. Both come from `make addons`.
2. Remove `/etc/cni/net.d/05-cilium.conflist`.
3. If `00-multus.conf` names another delegate, delete that node's Multus pod and wait until the new daemon writes the file naming Cilium's new path.
4. Assert that `00-multus.conf` is the only CNI file and names that path.

Step 2 comes before step 3. When the old daemon stops, it deletes `00-multus.conf`, and with Cilium's old file still there containerd would run Cilium alone until the new daemon writes its file. In this order a pod in that gap finds no network and waits. Until the restart, the old daemon cannot read its delegate, so a pod ADD there fails and the kubelet retries it.

**Why there.** The file lives on each node, outside every object Helm owns, so Helm cannot remove it, and Cilium does not. Ansible owns the node configuration and already reaches every node and the first control plane's `admin.conf`. `make addons` serves every Helm environment, and cel1 has no Multus, so a lab-only migration does not belong there. The role takes Cilium's directory from the same `helm/cilium/values-<env>.yaml` the runner reads, so the path is written once.
