# M3: hostNetwork RDMA pods and the Multus secondary network

> Date: 2026-11-16  
> Verdict: **Both scenarios passed and validated from wiped guests.** `k8s-hostnet-rdma` repeated the M1 RXE baseline between hostNetwork pods (run `20261116T002950Z`), and `k8s-multus-net1` showed `net1` from Whereabouts beside Cilium, through pod recreation and a worker reboot (run `20261116T003040Z`). The M1 and M2 scenarios still pass on the same guests. Every check failed once on a deliberate break and passed after the repair. The pods need `privileged`, and Multus leaves a window after each boot in which a new pod gets no `net1` (section 9).  
> Environment: the lab profile of the QEMU harness (cp1, worker1, worker2), Ubuntu 24.04.5, kernel 6.8.0-147-generic, rdma-core 50.0-2ubuntu0.2, perftest 24.01.0+0.38-1build2, Kubernetes v1.36.6, Cilium chart 1.20.4, Multus v4.3.2 thick plugin, Whereabouts v0.9.4. Guest disks lived under `/data/rfl-lab/m3`. The host had 24 cores and 87 GiB of available memory before the first boot, and no other guest ran (`evidence/m3/host-before-boot.txt`).

M3 answers two questions with two scenarios and two verdicts.

1. `k8s-hostnet-rdma`: can a container on a worker use the node's RDMA device and repeat the M1 baseline? It can. This shows only that a container uses the node's device. It shows no pod-private interface, no device isolation and nothing about Cilium's pod data path.
2. `k8s-multus-net1`: can Multus add a secondary IP network `net1` beside Cilium, with cluster-wide Whereabouts addresses, without breaking the primary network? It can. `net1` is an IP network only. It carries no RDMA device, provider or permission into a pod.

## 4. Probes before building

**Extra MACs on the lab link pass.** `tests/integration/qemu-lab/probe-m3.sh macvlan` put one macvlan child in bridge mode on `lab0` of each worker, inside a throwaway network namespace, with one of the last two pool addresses. Each side sent 5 echo requests and got 5 replies. tcpdump on both lab NICs shows the frames with the children's own source MACs `42:37:32:85:de:21` and `86:74:87:7f:96:b9`, and `lab0` stayed at promiscuity 0, because virtio-net takes the extra MACs into its filter (`evidence/m3/probe-macvlan.log`). So macvlan stays the secondary type. ipvlan, the IP alternative, was not needed and did not run.

**RXE lists the addresses of macvlan children.** While the children existed, `rxe0` on each worker had two more GIDs, the IPv4-mapped child address and its link-local address, with `ndev` naming the child, although the child sat in another network namespace. They vanished with the children. M1 sets no GID index, so the M1 scenarios ran again with `net1` pods present (section 7). rdma_cm still chose GID index 1.

**Multus picks Cilium and sorts first.** After `make addons`, every node held `00-multus.conf` of type `multus-shim` with `clusterNetwork` `/host/etc/cni/net.d/05-cilium.conflist`, and it sorts before `05-cilium.conflist`. containerd loads the first file by name. `whereabouts.d` is a directory and no candidate (`evidence/m3/cni-netd-after-multus.txt`, before: `cni-netd-before-multus.txt`).

| 4 | Profile 3 with `/dev/infiniband` as a hostPath | The files appear with mode 0666, but opening `uverbs0` and `rdma_cm` gives `Operation not permitted`: the device cgroup refuses them. `ibv_devinfo`: `Failed to open device`, exit 1. rping: `failed to create RDMA CM event channel` |

Kubernetes has no field that admits one character device to a container without a device plugin, and capabilities do not change the device cgroup. So profile 4 cannot work, and profile 5 is the narrowest that does. Every run proves profiles 3 and 4 fail again in `narrower-profiles-fail`, and proves through a dry-run relabel that `baseline` and `restricted` would refuse both pods in `pod-security-as-declared`.

**memlock.** The pods run with 8388608 bytes soft and hard, the default of containerd's systemd service, which sets no `LimitMEMLOCK`. The node's SSH user that the VM baseline runs as has 776622080 bytes. No profile hit an `ibv_reg_mr` memlock error. With containerd's limit lowered to 65536 bytes on worker2 (break `memlock-64k-on-worker2`, run `20261115T225629Z`), rping and Read, Write and Send with 4096 B x 1000 still passed, so these test parameters register less than 64 KiB. `memlock-in-pods` records both limits and fails when the two ends differ.

## 6. The scenarios

**`k8s-hostnet-rdma`.** One pod per worker in `lab_k8s_namespace`, pinned by the `kubernetes.io/hostname` label, `hostNetwork: true`, `dnsPolicy: ClusterFirstWithHostNet`, image by digest with `imagePullPolicy: Never`, `RFL_RUN=<run-id>` in the container's environment. The pods sleep and the runner starts every process through `kubectl exec` on cp1, under `timeout`. rping and perftest take server, client, ports, sizes, iterations and time limits from `vm-rxe.yaml`, so the pods repeat `vm-rxe-baseline` unchanged against the lab NIC addresses. The server counts as ready when `rdma resource show cm_id` inside its pod shows the listener. tcpdump captures every NIC of both nodes over the SSH path, as in M1. At the end the namespace is deleted, and the node's `/proc` must hold no process with the run id, inside a pod or not. Each process's `<check>/<guest>-<role>.context.json` names node, pod, container, RDMA device, lab address and command.

**`k8s-multus-net1`.** The runner renders the NetworkAttachmentDefinition from the inventory alone: namespace `lab_k8s_namespace`, master `lab_rdma_nic`, which must be the same on every worker, and the Whereabouts `range`, `range_start` and `range_end` from `lab_address_plan.rdma` and `lab_address_plan.multus_pool`. A pool that leaves the lab network or holds a node's `lab_rdma_ip` is refused too. `python -m run.multus render` prints it:

```yaml
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: rdma-lab-net
  namespace: rdma-lab
spec:
  config: '{"cniVersion": "0.3.1", "name": "rdma-lab-net", "type": "macvlan", "master":
    "lab0", "mode": "bridge", "ipam": {"type": "whereabouts", "range": "10.77.0.0/24",
    "range_start": "10.77.0.100", "range_end": "10.77.0.199"}}'
```

With an extra inventory that gave worker2 `lab_rdma_nic: other0`, render stopped with exit 2: `lab_rdma_nic differs across the workers (worker1 lab0, worker2 other0). One NetworkAttachmentDefinition names one macvlan master for every node ...` (`evidence/m3/breaks-3/15-refuse-differing-lab-nics.log`). The test pods are busybox at the PodSecurity `restricted` level, with no host network. The server serves its pod name over HTTP. The client fetches it over eth0 and over net1, and the lab NIC of both workers is captured. Pod recreation deletes both pods, waits until Whereabouts holds nothing for them, and starts them again. The reboot check deletes the client, reboots worker2 through `systemctl reboot`, and waits until the Node reports the new boot ID and the Multus pod there started after the boot.

## 9. Findings

**Multus removes its file when it stops.** The thick daemon runs `os.Remove(multusConfigFile)` when its config watcher ends on SIGTERM (`pkg/server/config/manager.go` at v4.3.2). During the reboot of worker2 in run `20261115T221719Z`, `kubectl logs --previous` of the old Multus pod showed `caught terminated, stopping...` (that output was not kept), and after the boot `/etc/cni/net.d` held only `05-cilium.conflist` (`evidence/m3/runs/20261115T221719Z/.../reboot-keeps-cni-order/worker2-ls.txt`) until the new daemon wrote `00-multus.conf` 18 to 19 seconds after the boot. In that window containerd runs Cilium alone, so a pod started then gets eth0 and no net1, without an error. The manifest has no readiness probe, so the Multus pod turns Ready before it writes the file. That first run read the directory at 22:19:33, less than a second before the file appeared at 22:19:34.103, and failed. The check now records the state at Multus Ready, waits up to `cni_settle_timeout_s` (60) for the settled order and records the gap as `reboot.multus_conf_absent_after_boot_s`.

**Multus keeps the delegate it found at start.** With `multusConfigFile: auto`, the daemon takes the first CNI file it sees as the default delegate when it starts and only watches that file. A file that sorted before Cilium's at boot became the delegate. After that file was deleted, `00-multus.conf` still named it, the daemon logged `failed to get clusterNetwork` on every ADD and never regenerated, and every new pod on that node stayed in `ContainerCreating`. Restarting the Multus pod on that node regenerated the file with Cilium (`evidence/m3/shadow/`).

**A capture stopped right after the traffic lost its last packets.** In run `20261115T221719Z`, worker1's lab capture held 0 frames while worker2's held the 5 and 5 frames of the net1 request. libpcap without immediate mode hands packets to tcpdump in buffer-timeout batches, and worker1's capture was stopped within a second of the request. The Multus runner now uses `--immediate-mode`, and every later run saw both directions on both lab NICs.

**`make rxe-up` did not recreate a deleted device.** The oneshot `rfl-rxe.service` stays active, so `state: started` did nothing after `rdma link delete`. The role now reads the links after the unit settings and restarts the unit when the device is missing. A rerun on a healthy worker still reports `changed=0`.

**Whereabouts gives freed addresses back.** After pod deletion released `10.77.0.100` and `10.77.0.101`, the recreated pods got the same two addresses, which they could not have if the old allocations had leaked.

**Multus `default-route` selection did not move the default route.** A pod whose network selection asked for `default-route` through the lab network kept its default route on eth0, with and without a gateway in the IPAM configuration. The break for `default-route-on-eth0` therefore uses IPAM routes, and the check also asks the kernel which interface reaches the first control plane's node address.

**`ENV=lab` now installs Multus and Whereabouts on the ha profile too.** The ha acceptance run installed all three releases at revision 1 and still passed (section 7).

## 10. What the results mean

- `k8s-hostnet-rdma` shows that a container on a worker can open the node's RXE device and run RDMA CM, Read, Write and Send against the lab NIC addresses, with the frames on the lab NIC only. The pods share the node's network namespace and the whole RDMA device. It does not show a pod-private interface, device isolation between pods, Cilium's pod data path or any way to run RDMA without `privileged`.
- `k8s-multus-net1` shows that Multus adds `net1` beside Cilium without moving the default route or breaking eth0 across nodes, that Whereabouts hands out cluster-wide addresses without duplicates and releases them, and that the CNI order recovers after a reboot. `net1` carries IP only. RXE lists `net1` addresses as GIDs, but no pod got an RDMA device on `net1`, and nothing here shows an RDMA endpoint for a `net1` address.
- Bandwidth is a software measurement of this host and guest pair with no pass threshold, as in M1.

## 11. Not run

- The VMware Workstation path. This host does not have it.
- ipvlan L2 on the lab NIC. macvlan passed the probe, so the alternative was not needed. ipvlan was never enabled, so it never shared a parent with macvlan.
- A pod-private RDMA path: an RXE device on `net1`, the RDMA CNI, RDMA subsystem exclusive mode or the RDMA shared device plugin. They are the optional experiment after M3.
- Hubble and Cilium NetworkPolicy on `net1` or on hostNetwork pods.
- A device plugin or CDI path that would admit `/dev/infiniband` without `privileged`.
