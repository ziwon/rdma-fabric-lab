## 3. A break says so in its manifest, and the report counts the latest real run

Before M7 `make report` listed every run directory ever made, deliberate breaks included, and only a directory name or a script's step table told a break from a failure. A run now records `deliberate_break` in its manifest. It is null for an ordinary run. A break names itself and what it does, for example `{"name": "missing-link", "description": "the simulator gets tracks/b-ibsim/topologies/b-01.net without the link at \"hca2\"[1]"}`. The Track B and Track C runners set it from their break tables. A script that breaks the environment before it calls a runner exports `RFL_BREAK` and `RFL_BREAK_WHAT`, which `rfl run-init` reads.

The field arrives with `schema_version` 2. The schema requires it in version 2 and forbids it in version 1, so the 258 run directories that existed before M7 validate unchanged. For version 1 manifests the report reads the parameter the two simulator tracks already recorded, `inputs.parameters.break_link` in Track B and `inputs.parameters.deliberate_break` in Track C. Track A and cel1 break runs of version 1 carry no marker, and each of them was followed by a passing repaired run, so none of them is the latest run of its scenario.

`make report` now prints, for each result kind, the required and the optional scenarios apart. For each scenario it shows the latest finished run that is not a break, and counts the older runs, the break runs and the unfinished runs it left out. A scenario spec without any run shows as `never ran`. The closing lines count the required and optional scenarios that passed. `make report STRICT=1` exits 1 unless every required scenario passed, and an invalid run directory still gives exit 4. Before M7 the report of the same results directory listed 258 rows. On that directory the new report counted 10 of 15 required scenarios passed, because no Track C run had been made in this checkout, and it left out 8 break runs, 6 unfinished runs and 231 older runs (`evidence/m7/report-before-m7-runs.txt`).

`tests/unit/test_rfl_manifest.py` covers the latest-run choice over an older failed run, a newer break and a newer unfinished run, the grouping, the strict exit, the exit 4, the environment variables, a refused break without a slug name or a description, version 1 validity and version 2 strictness, and the version 1 readers per track. Removing the break filter from `latest_runs`, or the version 2 rule from the schema, failed tests.

## 4. make collect and credentials

`make collect` records the host and the lab workers as a `vm-environment` run. Its guest snapshots are the OS, kernel, addresses, routes, RDMA links and system mode, `ibv_devinfo`, the RDMA NIC's netplan file, the RXE unit, journal and module file, held packages, CPU, memory and time sync. Its host snapshots are the kernel, OS, cores, memory, the QEMU version and the pinned Python tooling. It compares every `lab.*` lock value of scope `m1` with what the workers report. M7 added the resolved configuration: each worker's inventory variables as `ansible-inventory` resolves them, kept by the prefixes `lab_`, `k8s_` and `rfl_` and the connection variables `ansible_host`, `ansible_port` and `ansible_user`.

Nothing it writes may carry a credential. A variable whose name matches `pass`, `secret`, `token`, `private_key`, `key_file`, `kubeconfig`, `credential` or `cert` is never written, whatever its prefix. Every file passes a scan for a PEM private key, a kubeconfig client credential, a `token:` value and a password assignment before it is written. A file that matches is replaced by a note that names the shape of the match and none of its value, and the check `no-credential-collected` fails.

`tests/unit/test_lab_collect.py` runs the real `collect.main` against an inventory whose worker carries a private key path, a kubeconfig path, a join token, a become password and a registry secret, and against a guest that prints a private key for the netplan file. No secret string and no key header appears in any written file, the credential-named variables are absent, and the check fails only in the run with the key. A second test asserts that no snapshot command reads a kubeconfig, `admin.conf`, `/etc/kubernetes`, `.ssh`, an SSH key, `shadow`, a token or a secret. Dropping the name filter or the scan failed the test.

## 8. Defects found and fixed

Each fix below changes a track's behavior only to remove a defect this task found.

**Pods were killed at reboot without being stopped, after any rerun of `make rxe-up` or `make k8s`.** This made `k8s-multus-net1` fail `pod-at-boot-waits-for-multus` in `make track-a` of the first full run (run `20261116T165752Z`). The check found `00-multus.conf` already present at its first look after the reboot. The file's birth time, 1794847758.8, was 580 s before that boot. So the file had survived the reboot, and the check had no window to observe. The causal chain, each link measured on worker2 (`evidence/m7/multus-window/`):

1. `ansible/roles/rxe/tasks/main.yml` line 81 and `ansible/roles/containerd/tasks/main.yml` line 111, at `298fdcd`, passed `daemon_reload: true` on every run, changed or not.
2. On systemd 255.4-1ubuntu8.18, one `systemctl daemon-reload` emptied `Conflicts=shutdown.target` and `Before=shutdown.target` on the kubelet's slices `kubepods.slice` and `kubepods-burstable.slice` (`daemon-reload-probe.txt`). A `make rxe-up` that reported `changed=0` did the same (`step2-old-rxe-up.txt`).
3. The next shutdown then stopped no container scope. The serial console shows `systemd-shutdown[1]: Waiting for process: … (multus-daemon), … (sh), … (ip-control-loop)` and the restart about 31 s later (`worker2-serial-final.txt`).
4. Multus removes its file only 10 s after SIGTERM, when its watcher ends (`SigTermCancelAfter` in `cmd/multus-daemon/main.go` and `os.Remove` in `pkg/server/config/manager.go` at v4.3.2). It was still running when the guest restarted, so the file stayed. In the reboots where systemd stopped the scopes, one scope stopped 10 s after the others began to stop, which matches Multus's delay, and the file was gone after the boot. That scope's container was not identified, so the match is an inference.
5. Of worker2's six boots in that run, the two whose shutdown kept the file are the only two in which `vm-rxe-rerun` ran `make bootstrap` and `make rxe-up` on the live cluster (`worker2-scope-counts.txt`, `worker2-boots.txt`).

Rejected hypotheses: the run looked too late (the birth time precedes the boot); the removal did not reach the disk (systemd never sent the stop, so no removal happened); the watcher never started (Multus wrote the file in boot -4 at boot+18.8 s, and `multus-daemon` still ran at the end of both boots). Before the fix, a manual reload followed by a reboot kept the file, as predicted (`step1-reboot-after-manual-reload.txt`). After it, the fixed `make rxe-up` and `make k8s` reported `changed=0` and left the dependencies in place (`step3-fixed-roles.txt`). The reboot that followed stopped all 14 scopes, the file was absent at the boot, and Multus wrote a new one at boot+18 s (`step4-reboot-after-fixed-roles.txt`). Both tasks now leave the reload to their handlers, which run only when a unit file changed. `tests/unit/test_ansible_daemon_reload.py` fails when any role task or playbook reloads systemd outside a handler, and it flags the old rxe task. The check now says `00-multus.conf survived the reboot` in this case, tested on the captured output of run `20261116T165752Z`. With the fix, `k8s-multus-net1` passed in the killed-run proof's first attempt (`20261116T182146Z`), after a `make rxe-up` and a `make k8s` on the same boot.

**The Track C image digest depended on the umask of the checkout.** From a wiped guest, `make track-c CLEAN=1` built `sha256:2f14f43e…`, not the pinned `sha256:da7a3245…`. The two images differ in one layer and one bit: `/usr/local/bin/rfl-ns3` has mode 0755 in M6's archive and 0775 in M7's, with identical content (`evidence/m7/ns3-digest/layer-diff.txt`). `COPY rfl-ns3` (line 43 of `images/ns3/Dockerfile`) keeps the mode of the guest copy, and `synced_tar` (line 48 of `scripts/ns3/guest.py` at `298fdcd`) took that mode from the checkout, made here with umask 002. `synced_tar` of Track B and Track C now sends 0755 for directories and executable files and 0644 for the rest, the modes Git keeps. `tests/unit/test_guest_copy_modes.py` fails without it. `make track-c-image CLEAN=1` then gave `sha256:da7a3245…` again, so `ns3.image` did not change.

**The Track B image was not reproducible.** From a wiped guest, `make track-b` built `sha256:0b462da8…`, not the pinned `sha256:cb3e3550…`, which came from M4's cached build. M4 section 13 had listed a cache-free build as not tried. The old build left four sources of difference:
