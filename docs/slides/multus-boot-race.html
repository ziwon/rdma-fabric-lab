Speaker notes · 0:40–1:50 (1:10)

Separate the signals. A worker that reports Ready and a pod that runs do not establish that the pod received its second interface. In run 20261125T131218Z the pod met kubectl wait --for=condition=Ready. It asked for the network in its annotation and carried no network-status, because the runtime had called Cilium alone and that call succeeded.

On a GPU platform the second interface is how a pod reaches the RDMA or storage fabric, and nodes reboot for firmware, kernels and drivers. In this lab net1 is a macvlan IP network that stands in for that attachment.

Speaker notes · 1:50–3:05 (1:15)

Two ordinary pods on two workers, at the PodSecurity restricted level. Cilium gives each eth0 and the default route. Multus adds net1, a macvlan child of the lab NIC, and Whereabouts assigns its address.

Stock paths after a reboot: Cilium’s file was live at boot+6.2 s, Multus’s file at boot+18.5 s.
Speaker notes · 3:05–4:40 (1:35)

containerd uses the first CNI file in its directory. The Multus daemon removes 00-multus.conf when it stops, so a clean reboot starts without it. In the lab the file was gone after the Multus pod of a worker was deleted and back about 1.4 s later, written by the new pod. With the stock paths of both charts, Cilium’s file sits in the same directory and survives the reboot. In run 20261125T131218Z containerd reported a network from boot+6.2 s, and Multus wrote its file at boot+18.5 s.

The lab layout moves Cilium’s file to a directory that only Multus reads. Then containerd has no network until Multus writes its file, the kubelet holds the pod, and the pod starts with both interfaces. The class of failure is reported outside this lab: in Sylva issue 3962 a pod on a newly joined node started through Calico alone before Multus wrote 00-multus.conf, and no error was reported.

Speaker notes · 4:40–6:50 (2:10)

Demo sequence: show the two directories, reboot a worker, create a pod as soon as the node answers, and read the named checks. The slide shows two runs on one cluster built from wiped guests. With the stock CNI paths, run 20261125T131218Z: containerd reported a network in 24 of 24 samples while 00-multus.conf was absent, and began the pod’s sandbox at boot+16.2 s, before Multus wrote its file at boot+18.5 s. The 11 other checks passed, because the pods created before the reboot went through Multus.

After the move to the lab layout, run 20261125T132655Z: containerd had no network in all 22 samples until the file appeared at boot+17.5 s, the sandbox began at boot+18.2 s, and all 14 checks passed. The pod of the test tolerates every NoSchedule taint, so that only the container runtime can hold it. Ordinary pods do not tolerate those taints, and the next slide counts what happened to them.

These are recorded results, with the run IDs and three named verdicts shown on the slide.

Speaker notes · 6:50–8:05 (1:15)

The demo pod is the earliest pod a node can run. probe-boot-window.sh counts the ordinary ones, on the same cluster. Each round reboots worker2. Keepers are three pods already running there, which the kubelet starts again in new sandboxes. A waiter is one pod created while worker2 is down, scheduled once the node is Ready again. Five rounds of each gave 20 pod starts per layout. Multus wrote its file 17.7 to 19.8 s after boot, every one of those sandboxes began 9 s or more after it, and 0 of 20 lost net1 with the stock paths, as in the lab layout. The stock paths were safe by timing, not by design.

Then one more init container started the Multus daemon 30 s later, and its file appeared 48.6 to 50.2 s after boot. Over three rounds of each kind, the sandboxes still began 28.1 to 32.0 s after boot, and with the stock paths all 12 pods came back Ready without net1. The 9 restarted pods kept the network-status annotation of their old sandbox, which lists net1 and an eth0 address the pod no longer had. The 3 waiting pods had no annotation. In the lab layout 0 of 12 lost it, because every sandbox waited for the file. 18 s is not a property of Multus: on the 13-guest simulation of docs/fleet.md, the file appeared 53.3 s after boot. This is one host and three guests, so it gives no fleet-scale timing.

raw outputs it references.
scenario spec / named check / run manifest / raw evidence
Speaker notes · 8:05–9:15 (1:10)

The reusable part is the test design. Write the invariant before running the test. Induce one reversible bad state in a disposable environment and verify the relevant assertion catches it, rather than accepting any nonzero exit. Repair it and run the same check again. In this repository the break puts a copy of Cilium’s file back into the runtime directory of one worker, and the same three checks must fail.

The run manifest points back to the evidence. Deliberate failures are marked separately from the latest normal results.
