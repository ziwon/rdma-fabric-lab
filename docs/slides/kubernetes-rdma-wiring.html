Speaker notes · 1:50–3:15 (1:25)

The control plane schedules two ordinary pods or two hostNetwork test pods across separate worker VMs, depending on the scenario. On lane A, the hostNetwork pods see RXE on the worker lab NIC and the test verifies real software RDMA verbs: Read, Write, and Send. These pods are privileged, as uid 65534 with no host PID, host IPC or volume: with a narrower profile ibv_devinfo finds no device, which the check narrower-profiles-fail records. In run 20261125T120953Z both lab NICs carried 15334 RoCEv2 frames and the management NICs none. On lane B, Multus adds a macvlan interface to ordinary restricted pods and Whereabouts assigns their addresses. Cilium still supplies eth0. The lanes use the same lab underlay but measure different things: the lower lane does not exercise RDMA in the pod.

Cilium’s delegated config stays in its own directory.
Multus removes its file when it stops. After the reboot the copy was live at boot+6.1 s, Multus’s file at boot+18.7 s.
Speaker notes · 3:15–4:40 (1:25)

The intended layout separates the runtime-visible directory from Cilium’s own directory. In the documented regression, a copy of the Cilium conflist goes back into /etc/cni/net.d on worker2. The Multus daemon removes 00-multus.conf when it stops, so every boot starts without it. In the lab the file was gone after the Multus pod of a worker was deleted and back about 1.4 s later, written by the new pod. Early in boot, before Multus writes its config, the copy gives containerd a usable primary CNI too soon: in run 20261125T121324Z from boot+6.1 s, 12.6 s before Multus wrote its file at boot+18.7 s. An early test pod is deliberately scheduled as the worker returns. The test compares runtime readiness and the first sandbox creation against when the Multus config appears. This is a lab-specific regression, not a claim about all Cilium or Multus installs.

Speaker notes · 4:40–7:00 (2:20)

Demo sequence: show a healthy baseline; introduce only the stale Cilium config on worker2; run the reboot regression; inspect the named checks. Remove the stale file, rerun, and show the repaired verdict. For the talk, prefer a short recorded capture or these recorded runs to waiting on a live reboot.

The slide shows two runs of 2026-11-25 on a cluster built from wiped guests. In the broken run, 20261125T121324Z, containerd reported a network in 25 of 25 samples while 00-multus.conf was absent, first at boot+6.1 s, and began the pod’s sandbox at boot+16.4 s. Multus wrote its file at boot+18.7 s. The pod met kubectl wait --for=condition=Ready and had eth0 only. The 11 other checks passed, because the two pods created before the reboot went through Multus and had net1. In the repaired run, 20261125T121559Z, containerd had no network in all 25 samples until the file appeared at boot+18.7 s, the sandbox began at boot+20.5 s, and all 14 checks passed. The same break failed the same three checks on 2026-11-16, in run 20261116T053519Z.

The run evidence stays on the lab host under results/ and .lab/breaks-k8s-rdma/20261125T121319Z/pairs.tsv. The repository stores the three summary rows of each run as the excerpts slides-net1-break and slides-net1-repair, and a test compares this slide with them. Keep the run IDs when the slide changes, and do not invent a screenshot or a run ID.

The lab gives each test an evidence type so the claims stay separate.

MULTUS NET1
Passed across worker nodes

PRODUCTION FABRIC
Outside this test
No HCA, physical InfiniBand or NCCL benchmark.
Speaker notes · 7:00–8:05 (1:05)

Be explicit about what each scenario can show. The hostNetwork case exercised the software RDMA provider, and its pods had to be privileged to reach the device. The Multus case did not expose an RDMA device to ordinary pods, and its reachability test is IP. This slide’s claims do not carry over to a real HCA, switches, physical InfiniBand, production throughput or NCCL. The repository also has separate simulations. Those are out of scope for this talk.

Speaker notes · 8:05–9:15 (1:10)

The reusable part is the test design. Write the invariant before running the test. Induce one reversible bad state in a disposable environment and verify the relevant assertion catches it, rather than accepting any nonzero exit. Repair it and run the same check again. The run manifest points back to the evidence. Deliberate failures are marked separately from the latest normal results.
